## 二、技术选型（不从 0 写，集成成熟轮子）

### 2.1 前端：Tremor Raw + shadcn/ui

| 方案 | GitHub | 选择理由 |
|------|--------|----------|
| **Tremor Raw** | [tremorlabs/tremor](https://github.com/tremorlabs/tremor) ⭐3.5k | 35+ 开箱即用数据看板组件（AreaChart/BarChart/DonutChart/KPI Card/Table），基于 Recharts+Radix，MIT 协议，直接替换现有 recharts 裸调用 |
| **shadcn/ui** | [shadcn-ui/ui](https://github.com/shadcn-ui/ui) ⭐80k+ | 表单/弹窗/导航组件，Admin 后台用，copy-and-paste 无依赖锁定 |
| **Tremor Dashboard Template** | [tremorlabs/template-dashboard-oss](https://github.com/tremorlabs/template-dashboard-oss) | 直接 fork，Next.js App Router + TypeScript + Tailwind，省去脚手架搭建 |

**现有代码影响**：
- `app/viz/page.tsx` 的 `OverviewSection`、`Top20Section` 等组件——图表部分替换为 Tremor `AreaChart`/`BarChart`/`DonutChart`
- 业务逻辑（数据过滤/分组）保留，只换渲染层
- 无需重写 `api.ts`，接口不变

### 2.2 采集调度：Prefect 3（替换自研 WorkflowEngine）

| 方案 | 选择理由 | 不选原因 |
|------|----------|----------|
| **Prefect 3** | 单人 Python-first，`@flow` + `@task` 装饰器即可迁移现有脚本；本地运行无需云服务；内置 UI dashboard 替代 Admin 后台任务监控部分 | Dagster 学习成本高，资产模型对本项目偏重 |
| Airflow | — | 运维成本高，1 人团队不合适 |
| APScheduler | — | 无状态持久化，无 UI，比现有方案进步有限 |

**现有代码迁移路径**：
```
现有：WorkflowEngine.run_task() → subprocess.run(script.py)
目标：@task def run_collector(task_id) → collector.runner.run_pipeline_task(task_id)
     @flow def weekly_collection_flow() → 调度多个 task
```
- `state_store.py`（SQLite）→ Prefect 内置状态存储替代（或保留作业务级日志）
- `login_wall_handler.py` → 保留，集成为 Prefect task 的 failure hook

### 2.3 反爬/采集：Crawlee-Python + Camoufox

| 方案 | GitHub | 适配点 |
|------|--------|--------|
| **crawlee-python** | [apify/crawlee-python](https://github.com/apify/crawlee-python) ⭐9.4k | 统一 HTTP + 浏览器接口，内置 SessionPool（解决登录墙），proxy rotation，持久化请求队列 |
| **Camoufox** | [daijro/camoufox](https://github.com/daijro/camoufox) | Playwright 替代内核，绕过 Amazon/Shopee 等强反爬，直接插入 `PlaywrightCrawler` |

**现有代码迁移**：
- `AmazonReviewScraper`、`ShopeeBrowserAdapter` → 改造为 `PlaywrightCrawler` subclass
- `YoutubeCommentProbeAdapter` → `BeautifulSoupCrawler`（HTTP 即可）
- `GenericStaticAdapter` → `HttpCrawler`
- `login_wall_handler.py` 检测逻辑 → 迁移为 crawlee `SessionPool` 的 `is_blocked` hook

### 2.4 数据验证：Pandera

| 方案 | GitHub | 适配点 |
|------|--------|--------|
| **pandera** | [unionai-oss/pandera](https://github.com/unionai-oss/pandera) ⭐3.5k | 用 Python dataclass 定义 CSV schema，替换现有手写 `validate_viz_dataset.py`；与现有纯 Python（无 pandas）兼容，可直接验证 dict list |

**现有代码影响**：
- `tools/validate_viz_dataset.py` → 重写为 pandera schema 定义 + 一行 validate 调用
- `tools/cleaning/_common.py` → 每个 `clean_*.py` 增加输出 schema 校验

### 2.5 文档：VitePress（选配，月内不做，记录备用）

- 项目内文档维持 Markdown，暂不引入额外工具
- 如后续需要对外展示，用 [VitePress](https://vitepress.dev/) 一键生成静态站

## 三、数据架构重构

### 3.1 确立唯一真源

```
唯一写入点：data/delivery/tables/*.csv（12 张 CSV）
            ↓ tools/export_viz_json.py
唯一读取点：data/delivery/viz_dataset.json（merged）
            data/delivery/viz_country_insight.json
            data/delivery/viz_opportunity.json
            data/delivery/viz_opportunity_internal.json

禁止直接修改 JSON 文件
禁止直接修改 xlsx（xlsx 只作为人工录入中转，录入后转 CSV）
```

### 3.2 数据分层（对齐数据字典已定义的分层）

```
ODS  data/raw/                     ← 采集原始输出（不修改）
DWD  data/processed/<国家>/dwd/    ← collector pipeline 标准化输出
DWS  data/delivery/tables/         ← 聚合指标 CSV（12 张，唯一真源）
ADS  data/delivery/*.json          ← 应用层，由 export_viz_json.py 生成
```

### 3.3 后端服务统一（消除 4 个独立 lru_cache）

**现状问题**：
- `country_service.py` 读 `viz_dataset.json`
- `dataset_service.py` 读 4 个 JSON，各自独立 `lru_cache`
- `insight.py` 直接读 `data/processed/insight_*.json`
- reload 时需要手动清 4 个 cache

**目标**：
```python
# services/data_store.py — 统一单例
class DataStore:
    _instance: ClassVar[DataStore | None] = None
    
    def reload(self) -> None:
        """一次调用，清所有缓存"""
        ...
    
    @property
    def merged(self) -> dict: ...
    
    @property  
    def country_insight(self) -> dict: ...
    
    @property
    def opportunity(self) -> dict: ...
    
    @property
    def opportunity_internal(self) -> dict: ...
```

**对 API 层影响**：所有 router 从 `DataStore.get_instance()` 取数，`/api/v1/admin/reload` 调用 `DataStore.reload()` 即清所有缓存。

## 五、项目管理

### 5.1 工作流约定

```
main 分支 = 可随时运行的稳定版本
feature/* = 每个阶段任务开一个分支
每个阶段结束 → 合并 main → 打 tag（v0.x）
```

### 5.2 风险管理

| 风险 | 概率 | 应对 |
|------|------|------|
| crawlee 替换 Amazon adapter 后采集失败 | 中 | 保留原 adapter 作 fallback，双跑对比 1 周 |
| Tremor 组件与现有数据结构不匹配 | 低 | Tremor 接受任意 recharts-compatible data，只需调整字段映射 |
| DataStore 重构导致 API 回归失败 | 中 | 重构前先写 `test_backend.py` 的完整 smoke test，重构后跑通再删旧代码 |
| Prefect 引入周期变长 | 高 | Prefect 设为选配，阶段二核心是 crawlee 集成，Prefect 可推迟 |

### 5.3 不做的事（明确边界）

- ❌ 不引入 PostgreSQL（DuckDB 本地文件已够用）
- ❌ 不做多用户权限系统，1 人使用无需
- ❌ 不做 CI/CD 流水线，手动运行即可
- ❌ 不做对外 API 文档（Swagger 保留即可）
- ❌ 不重写 `tools/cleaning/` 的清洗逻辑，只加 schema 校验
- ❌ NLP/AI 洞察（第二阶段，DuckDB 地基搭好后）

## 十一、DuckDB 数据仓库方案

### 11.1 仓库文件结构

```
data/
├── warehouse/
│   └── voc.duckdb          ← 单一数据库文件（ODS+DWD+DWS+ADS视图全在此）
├── raw/                     ← ODS原始文件（CSV/JSON，不入库，按需 ATTACH）
├── processed/               ← DWD标准化CSV（collector pipeline输出）
└── delivery/
    ├── tables/              ← DWS聚合CSV（12张，保留作ETL输入）
    └── *.json               ← ADS JSON（过渡期保留，DuckDB视图稳定后废弃）
```

**设计原则**：
- 单文件，本地运行，零运维
- DuckDB 直接 `read_csv_auto()` 读取现有CSV，无需手动建表+导入
- FastAPI 后端改为查 DuckDB，JSON 文件作过渡期兜底

### 11.2 核心 DDL

```sql
-- ODS：原始采集内容（直读CSV，不物化）
CREATE OR REPLACE VIEW ods_voc_content_raw AS
SELECT * FROM read_csv_auto('data/raw/**/**.csv', hive_partitioning=true);

-- DWD：标准化明细表（物化，主要写入层）
CREATE TABLE IF NOT EXISTS dwd_voc_content_std (
    voc_content_sk      VARCHAR PRIMARY KEY,
    collect_batch_id    VARCHAR NOT NULL,
    collect_date        DATE NOT NULL,
    country_code        VARCHAR(10) NOT NULL,
    country_name_cn     VARCHAR,
    platform_code       VARCHAR(50) NOT NULL,
    product_line_code   VARCHAR(50),
    content_type_std    VARCHAR(50),    -- post/comment/video/video_comment
    body_std            TEXT,
    title_std           VARCHAR,
    publish_time        TIMESTAMPTZ,
    lang_code           VARCHAR(10),
    like_cnt            INTEGER DEFAULT 0,
    reply_cnt           INTEGER DEFAULT 0,
    view_cnt            INTEGER DEFAULT 0,
    is_verified_purchase BOOLEAN DEFAULT FALSE,
    source_url          VARCHAR,
    competitor_brand    VARCHAR,
    pain_category       VARCHAR,
    sentiment_label     VARCHAR,        -- 预留：NLP阶段填入
    embedding_id        VARCHAR,        -- 预留：向量阶段填入
    content_quality_score FLOAT,        -- 信息源权重评分
    created_at          TIMESTAMPTZ DEFAULT now()
);

-- DWS：国家×品线×平台×日 聚合
CREATE OR REPLACE VIEW dws_voc_country_line_day AS
SELECT
    collect_date::DATE          AS dt,
    country_code,
    product_line_code,
    platform_code,
    COUNT(*)                    AS content_cnt,
    SUM(CASE WHEN sentiment_label='负面' THEN 1 ELSE 0 END) AS negative_cnt,
    SUM(CASE WHEN sentiment_label='正面' THEN 1 ELSE 0 END) AS positive_cnt,
    AVG(content_quality_score)  AS avg_quality_score,
    SUM(like_cnt)               AS total_likes
FROM dwd_voc_content_std
GROUP BY 1,2,3,4;

-- ADS：国家洞察摘要视图（替代 viz_country_insight.json）
CREATE OR REPLACE VIEW ads_country_overview AS
SELECT
    country_code,
    country_name_cn,
    COUNT(DISTINCT platform_code)           AS platform_cnt,
    COUNT(*)                                AS total_voc_cnt,
    SUM(negative_cnt)                       AS total_negative,
    MAX(dt)                                 AS last_updated
FROM dws_voc_country_line_day d
GROUP BY country_code, country_name_cn;
```

### 11.3 ETL Pipeline

```python
# tools/etl/load_to_duckdb.py
import duckdb
from pathlib import Path

DB_PATH = Path("data/warehouse/voc.duckdb")
DWD_GLOB = "data/processed/**/dwd/*.csv"

def etl_dwd_to_warehouse():
    """把 collector pipeline 输出的 DWD CSV 增量导入 DuckDB"""
    con = duckdb.connect(str(DB_PATH))
    con.execute(f"""
        INSERT OR IGNORE INTO dwd_voc_content_std
        SELECT
            voc_comment_sk          AS voc_content_sk,
            collect_batch_id,
            collect_date::DATE,
            country_code,
            country_name_cn,
            platform_name           AS platform_code,
            NULL                    AS product_line_code,
            'comment'               AS content_type_std,
            comment_text            AS body_std,
            NULL                    AS title_std,
            NULL::TIMESTAMPTZ       AS publish_time,
            NULL                    AS lang_code,
            0                       AS like_cnt,
            0                       AS reply_cnt,
            0                       AS view_cnt,
            FALSE                   AS is_verified_purchase,
            root_content_url        AS source_url,
            NULL                    AS competitor_brand,
            NULL                    AS pain_category,
            NULL                    AS sentiment_label,
            NULL                    AS embedding_id,
            NULL                    AS content_quality_score,
            now()
        FROM read_csv_auto('{DWD_GLOB}', hive_partitioning=false)
        WHERE comment_type != 'status'   -- 过滤登录墙状态行
    """)
    con.close()

def etl_dws_csv_to_warehouse():
    """把现有12张DWS CSV导入DuckDB（过渡期，保留CSV真源）"""
    con = duckdb.connect(str(DB_PATH))
    tables_dir = Path("data/delivery/tables")
    for csv_file in tables_dir.glob("*.csv"):
        table_name = f"dws_{csv_file.stem}"
        con.execute(f"""
            CREATE OR REPLACE TABLE {table_name} AS
            SELECT * FROM read_csv_auto('{csv_file}', header=true)
        """)
    con.close()
```

            SELECT dt, platform_code, content_cnt, negative_cnt

## 十二、信息源质量与权重体系

### 12.1 权重维度定义

每条 VOC 数据的质量由 5 个维度决定：

| 维度 | 字段 | 权重占比 | 说明 |
|------|------|----------|------|
| 平台权威性 | `platform_weight` | 40% | 电商评论 > 专业社区 > 社媒内容 |
| 内容深度 | `body_length_score` | 25% | 字数越多信息量越大，上限300字 |
| 互动权重 | `engagement_score` | 20% | 点赞+回复数，log缩放防头部效应 |
| 时效性 | `recency_score` | 10% | 90天内满分，线性衰减至365天 |
| 可信度 | `trust_score` | 5% | 验证购买者/实名用户加分 |

### 12.2 平台权重基线表

| 平台 | 基础权重 | 理由 |
|------|----------|------|
| Amazon verified review | 90 | 验证购买，强相关，意图明确 |
| TrustPilot | 85 | 实名评价，品牌直接相关 |
| Okendo（DTC品牌官网）| 80 | 真实购买者，高意图 |
| Reddit 母婴社区 | 75 | 深度讨论，社区验证，信息密度高 |
| BabyCenter / What to Expect | 70 | 垂直母婴社区，高相关性 |
| YouTube 产品测评评论 | 65 | 有参考视频内容，上下文丰富 |
| Amazon unverified review | 60 | 可能刷评，降权 |
| Twitter/X 产品讨论 | 50 | 碎片化，噪音高，但时效性强 |
| TikTok / Instagram 评论 | 45 | 娱乐属性强，与购买决策相关性较低 |
| 本地论坛（非垂直）| 40 | 语言/相关性参差不齐 |
| Facebook 群组讨论 | 35 | 封闭生态，可信度难验证 |

### 12.3 内容质量评分 SQL

```sql
-- 在 DuckDB 中计算 content_quality_score（0-100）
UPDATE dwd_voc_content_std
SET content_quality_score = LEAST(100, GREATEST(0,
    -- 平台权重 40分
    (SELECT base_weight FROM dim_info_source_quality
     WHERE platform_code = dwd_voc_content_std.platform_code) * 0.40
    +
    -- 内容深度 25分：字数/300，上限25
    LEAST(25, (LENGTH(body_std) / 300.0) * 25)
    +
    -- 互动权重 20分：log(1+likes+replies)/log(1+100) * 20
    LEAST(20, (LN(1 + like_cnt + reply_cnt) / LN(101)) * 20)
    +
    -- 时效性 10分：90天内满分，线性衰减
    GREATEST(0, 10 - GREATEST(0, (current_date - collect_date - 90)) * (10.0/275))
    +
    -- 可信度 5分
    (CASE WHEN is_verified_purchase THEN 5 ELSE 0 END)
));
```

### 12.4 dim_info_source_quality 扩展

现有表只有 P0-P3 分级，扩展为：

    priority_level      VARCHAR(2),   -- P0/P1/P2/P3（保留现有）

    access_mode         VARCHAR,      -- public/login/manual
    data_type           VARCHAR,      -- review/comment/post/video_comment

### 12.5 权重在产品中的应用

**聚合层**：VOC 统计不再是简单计数，改为加权计数：
```sql
-- 高权重来源的负面 VOC 更值得关注
SELECT country_code, pain_category,
    COUNT(*) AS raw_cnt,
    SUM(content_quality_score) / 100.0 AS weighted_cnt  -- 加权声量
FROM dwd_voc_content_std
WHERE sentiment_label = '负面'
GROUP BY 1, 2
ORDER BY weighted_cnt DESC;
```

**告警策略**：
- 高权重来源（≥70分）负面激增 → 立即告警（P0，影响品牌声誉）
- 中权重来源（40-70分）负面激增 → 次日汇总推送（P1）
- 低权重来源（<40分）负面 → 只纳入趋势统计，不触发告警

**看板展示**：国家详情页增加「数据源可信度分布」，展示各平台权重占比，让业务团队理解数据基础。
