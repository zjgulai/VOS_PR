# PR 与 SI PRD 完整对比及选择建议

## 0. 文档结论

本次不建议从 PR、SI 两个目录中分别挑选一份文件原样执行。八份材料包含战略愿景、外部研究、实施计划和研发 PRD，文档类型不同，直接按篇幅、版本号或总分淘汰会丢失必要信息。

推荐决策：

| 产品 | 推荐选择 | 决策状态 | 结论把握 |
|---|---|---|---|
| PR Intelligence | `implementation_plan` 作为上游业务与治理蓝图；正式 `PRD` 作为唯一研发主规格；`pplx` 作为带时间戳的研究附录；`ds` 归档为概念稿 | 有条件推荐 | 中 |
| Social Intelligence | 以基础版 `PRD` 为治理和数据契约骨架，吸收 `v2` 的业务内容与 YouTube/Reddit 数据契约，以 `v3` 的 S1 + Action 作为薄切思路；P0 平台顺序调整为 YouTube 优先、Reddit 并行；`ds` 仅保留愿景与报告结构 | 有条件推荐 | 中 |

条件尚未满足的原因不是文档不完整，而是缺少业务签字、真实工作流 baseline、平台商业授权、责任人和 Go/No-Go 标准。

表中的「有条件推荐」仅指推荐怎样组织和合并文档，不表示产品已经通过实施门槛。

> 重要边界：PR 与 SI 的总分只能分别用于各自目录内部比较，不能用来判断两款产品谁更值得做。

## 2. 两套完整比较方案

### 2.1 方案一：硬门槛 + 加权证据矩阵

适用阶段：当前的意图澄清与文档筛选。

先检查硬门槛，再评分。评分只评估候选文档是否完整表达了相关问题、机制、约束和验收设计，用于识别主骨架和需吸收的模块；不衡量真实业务价值或实施准备度。

| 维度 | 权重 | 核心问题 |
|---|---:|---|
| 业务需求契合度 | 25% | 是否命中真实、高频、高损失的部门问题 |
| 业务价值与决策作用 | 20% | 是否改变决策、时效、质量或结果，而不只是汇总信息 |
| 数据及证据可行性 | 15% | P0 数据是否可获得、可追溯、可持续、可删除 |
| P0 聚焦度与落地成功率 | 15% | 是否形成最短业务闭环，依赖和 Done Criteria 是否清楚 |
| 决策可信度与治理 | 10% | 是否区分事实、推断、未知，是否有审批、审计与失败处理 |
| 组织流程与采用概率 | 10% | 是否进入现有角色、节奏、任务、审批和复盘流程 |
| 指标及验收可验证性 | 5% | 是否有 baseline、口径、阈值、样本和 Go/No-Go |

计算公式：

```text
加权总分 = Σ（维度权重 × 维度评分 ÷ 5）
```

文档设计完整度评分锚点：

- 5：文档完整定义问题、机制、边界、失败路径、指标和验收，并明确列出未知项。
- 4：主体设计完整，仍有少量内部冲突、遗漏或未明确的依赖。
- 3：主要链路成立，但存在明显范围、机制或验收缺口。
- 2：只覆盖部分环节，或严重依赖作者推断。
- 1：只有概念，缺可执行机制。
- 0：文档缺失该维度，或自身表述互相冲突到无法使用。

证据等级 A–U 与文档分数分开记录。文档可以获得 5 分设计分，但真实证据仍为 B、C 或 U；此时不得据分数进入实施。半分仅用于记录文件间相对差异，不代表统计精度。

### 2.2 方案二：真实业务场景 Bake-off

适用阶段：方案一筛出前两名后，或争议模块会改变 P0 时。

所有候选使用同一批输入，运行同一条链路：

```text
触发 → 数据 → 分析 → 证据 → 建议 → 人工决策 → Action → 结果记录
```

| 维度 | 权重 |
|---|---:|
| 业务任务完成度 | 25% |
| 事实准确性与证据可追溯性 | 25% |
| Action 的业务可用性 | 20% |
| 数据覆盖和失败降级能力 | 15% |
| 时效与人工成本 | 10% |
| 审批、权限与治理 | 5% |

任一 P0 场景出现事实编造、证据断链、把缺失写成零或越权自动执行，直接不通过。Fixture 只能证明逻辑可运行，不能证明真实数据源和商业授权成立。

### 2.3 推荐使用顺序

1. 先按文档类型归位。
2. 用方案一筛选主骨架和冲突模块。
3. PR、SI 分别保留前两名或争议最大的 P0。
4. 用方案二完成业务盲评和数据验真。
5. 分别形成 PR canonical PRD、SI canonical PRD。
6. 最后抽取共享数据与 Agent 底座。

## 3. 证据等级与硬门槛

### 3.1 证据等级

| 等级 | 定义 | 可支持的结论 |
|---|---|---|
| A | 业务负责人签字、真实系统数据、有效合同、真实演练或 UAT | 可以形成正式决策 |
| B | 业务原话、可追溯项目事实、完整方法和验收设计 | 可以形成有条件推荐 |
| C | 外部案例、研究结论、方案建议，仍依赖内部确认 | 只能作为候选依据 |
| D | 概念陈述、演示样例、未经验证的假设 | 不能单独决定 P0 |
| U | 材料缺失或无法判断 | 必须补证据 |

当前材料没有方案达到完整 A 级：尚未看到两部门签字、真实 baseline、供应商权利合同和 UAT 结果。

### 3.2 七项硬门槛

1. P0 功能可追溯到部门确认的业务问题。
2. 至少有一个获准、可持续、可降级的真实数据入口。
3. 结论能回溯来源、采集时间、覆盖范围和不确定性。
4. 抓不到、字段缺失和真实零值可以区分。
5. 对外发布、媒体联系、Creator 联系和风险响应必须人工审批。
6. P0 有核心用户、负责人、交付物和可运行验收剧本。
7. 未验证能力不得包装成当前已具备能力。

硬门槛优先于总分。高分但硬门槛未通过，仍不得进入实施。

### 3.3 未知项的保守与乐观边界

真实实施准备度不使用本文的文档设计分。当前两款产品在业务优先级、商业授权、真实 owner、baseline、UAT 和 Go/No-Go 上均存在决策级 `U`。

若严格按「U 的保守下界为 0、乐观上界为 5」计算，PR 和 SI 各候选的真实准备度区间都会大范围重叠；在最严格口径下均可扩展到 0–100。这个区间没有排序能力，因此本文不发布伪精确的「真实准备度总分」。

| 产品 | 保守下界 | 乐观上界 | 当前可下结论 |
|---|---:|---:|---|
| PR Intelligence | 未通过实施门槛 | 完成全部确认与验真后重新评分 | 只能选择文档组合，不能决定实施就绪 |
| Social Intelligence | 未通过实施门槛 | 完成全部确认与验真后重新评分 | 只能选择文档组合，不能决定实施就绪 |

### 4.3 PR-IMP：业务与治理蓝图

事实：

- 将产品定义为 Evidence-first PR Action System，覆盖业务、法务、安全、CX、数据与技术角色。
- 设定美国英语市场、pumping/feeding、20–40 家媒体、8–12 个竞品的 12 周 MVP。

优势：业务价值、治理边界、组织运行和 P0 薄切最完整。

扣分与未知：内部数据、供应商、真实 owner、baseline、成本和外部事实仍未确认；它不是可直接替代正式 PRD 的研发规格。

结论：总分第一，但正确用法是作为上游蓝图，不是淘汰 PR-PRD。

### 4.4 PR-PRD：研发主规格

事实：

- 状态为「待业务评审」。
- 提供用户角色、权限、七个核心模块、失败路径、数据契约、评分、输出、性能指标和验收剧本。
- Document、Claim、Evidence、Risk、Opportunity、Action 的语义和证据门最完整。
- 通过本地 `qiaomu-ai-prd` 结构检查。

优势：四份中最适合研发与 AI 编程助手执行，数据、接口、状态和验收最明确。

扣分与未知：P0 同时包含数据源、媒体、风险、机会、媒体画像、周报和 Action，仍偏宽；内置自检命令错误指向不存在的 `VR` 路径；供应商和真实审批链未确认。

结论：应保留为唯一研发主规格，在业务确认后收窄 P0。

### 4.5 PR-PPLX：研究与采购附录

事实：

- 将需求从「搜新闻」重定义为 PR 决策支持系统。
- 覆盖外部品牌、媒体、竞品、行业、评分、KPI、RACI 和 build/buy/hybrid 路径。
- 有版权、平台 ToS、人工审核和 AI 失效防护说明。

优势：外部研究、媒体策略、竞品与采购视角最丰富。

扣分与未知：场景优先级和产品模块阶段定义互相冲突；外部来源本轮未重新核验；部分指标、权重和行业比较尚无内部 baseline。

结论：不作为研发主文档；将可复用事实放入带 `verified_at` 的研究附录。

### 4.6 PR-DS：愿景概念稿

事实：

| 能力 | 为什么必须在 P0 | 最小验收 |
|---|---|---|
| Source & Rights + Document/Claim/Evidence | 没有来源和权利，任何高影响结论均不可用 | 一条获准媒体源和一条监管源完成来源、时间、权利和证据回溯 |
| 预警与 Action | 没有风险升级、责任人和结果记录，P4 只会退化为负面信息汇总 | 风险信号能转为待确认或待审批 Action，不能跳过人工判断 |
| Coverage 与质量治理 | 防止把抓不到写成零、把模型推断写成事实 | 401、429、schema 变化、空结果和真实零值分别可见 |

推荐的 P0 候选闭环：

```text
获准数据源
  → Evidence Card
  → P4 风险候选与置信度
  → 人工确认、分级与升级
  → 风险 Action
  → 处置结果回填
```

周报、P3 媒体机会、P1 品牌健康度和其他完整业务模块不进入这个 P0。P4 的分类阈值、响应时限、责任人和成功标准将在下一决策门确认。

### 5.1 P4 P0 试点边界

产品规划层已确认 P0 试点限定为「美国市场 + 英语 + pumping/feeding 品类」。三项边界同时成立，才进入 P0 的正式监测、评估和验收范围。

| 维度 | P0 纳入规则 | 当前缺口 |
|---|---|---|
| 市场 | 风险与美国消费者、美国在售产品/SKU、美国监管或美国业务影响存在明确关联 | 监管源清单、目标渠道和地域判定规则待确认 |
| 语言 | 英语内容进入正式识别、分类和质量验收 | 非英语来源只记录 coverage gap，不据此声称「没有风险」 |
| 品类 | 只覆盖 pumping/feeding 及最终纳入清单中的产品/SKU | 产品、SKU、型号、历史名称和常见别名待业务提供 |

来源的发布地或域名不是唯一地域判断依据。美国以外发生的事件，只有在能够证明其与美国在售产品/SKU、美国监管或美国业务影响直接相关时，才进入 P0；否则作为范围外信息保留，不计入主指标分母。

扩展到新的市场、语言或品类前，必须重新确认数据权利、监管源、实体 taxonomy、gold set、baseline、SLA 和 UAT 样本。试点期间不得在不调整验收口径的情况下扩大范围。

### 5.2 P4 P0 风险边界

产品规划层已确认首期只覆盖以下四类风险。一个事件可以命中多个类别，但必须关联可核验来源和 Evidence Card，不能仅凭模型推断进入危机流程。

| P0 风险类别 | 首期识别对象 | 仍需业务确认 |
|---|---|---|
| 产品安全、召回与监管 | 伤害或安全隐患、产品缺陷、召回信号、监管调查或处罚风险 | 产品/SKU 范围、监管源、严重度与升级阈值 |
| 隐私与数据 | 数据泄露、未经授权的数据处理、隐私权利或数据合规风险 | 适用地区、敏感数据范围、Privacy owner 与升级路径 |
| 误导性宣传与评价真实性 | 产品或健康效果 claim 风险、虚假或操纵评价、未披露商业关系等真实性问题 | 禁用 claim、证据标准、Legal/Safety 审批边界 |
| 快速升级的负面舆情 | 跨来源扩散、关键账号或媒体放大、传播速度异常上升且可能造成品牌或业务损害的事件 | 升级速度、影响范围、关键来源和去重阈值 |

以下内容默认不进入 P4 危机流程，可以转入一般 PR/SI 洞察或客户服务队列：

- 无系统性证据的单条差评或一般负面表达。
- 不涉及安全、合规或舆情升级的日常客户服务问题。
- 与 Momcozy、在售产品或目标市场没有明确关联的行业和竞品信息。
- 缺少原始来源、时间或关键证据，只能由模型猜测成立的风险判断。

上述四类是 P0 的产品规划边界，不等于 PR、Legal/Safety/Privacy 已完成签字。新增第五类风险必须重新评估数据源、owner、SLA、gold set 和验收样本，不在试点中静默扩展范围。

### 5.3 P4 P0 风险分级

产品规划层已确认统一采用 `Sev0–Sev4`，其中 `Sev0` 最低、`Sev4` 最高。分级使用四个维度：安全/监管影响、影响范围、证据可信度和传播速度。

| 维度 | 需要判断的问题 | 使用规则 |
|---|---|---|
| 安全/监管影响 | 是否可能造成人身伤害、召回、监管调查、执法、重大隐私或其他不可逆损害 | 作为严重度底线；单个高影响信号不能因声量低而自动降级 |
| 影响范围 | 涉及多少产品/SKU、消费者、渠道、市场或关键利益相关方 | 范围扩大可以提高等级；具体量化阈值待 baseline 和样本确认 |
| 证据可信度 | 来源权威度、多源印证、原始证据完整性和事实一致性如何 | 与 `severity_level` 分开记录；低可信度触发优先核验，不直接消除潜在高严重度 |
| 传播速度 | 信号是否持续、加速或被关键账号、媒体和监管主体放大 | 用于判断升级紧迫性；具体时间窗口和增速阈值待确认 |

五级语义采用以下统一口径。表中的动作是产品设计建议，owner、通知渠道和 SLA 仍需业务签字。

| 等级 | 统一语义 | P0 默认处理 |
|---|---|---|
| `Sev0` 观察 | 弱信号或低影响单点，暂不构成可升级事件 | 留痕、去重并继续监测 |
| `Sev1` 关注 | 出现重复信号或可信负面信息，但影响仍局部且无明显升级迹象 | 进入人工工作队列并补充证据 |
| `Sev2` 升级 | 出现安全、隐私、真实性或监管风险，或传播速度明显上升 | 创建完整 Evidence Card，通知指定风险 owner 核验 |
| `Sev3` 严重 | 权威来源、多源扩散或可能造成重大法律、品牌或业务影响 | 创建 incident，启动 War Room 候选流程并限制相关外发建议 |
| `Sev4` 危急 | 涉及生命安全、召回、执法、重大数据泄露或同等级不可逆影响 | 进入最高优先级人工升级流程；系统不得自动对外发布或处置 |

分级顺序：

1. 先判断事件是否处于已确认的市场、语言、品类和四类风险范围内。
2. 再根据安全/监管影响确定严重度底线。
3. 使用影响范围和传播速度判断是否需要升级。
4. 单独记录证据可信度和待核验项，不用低可信度覆盖高影响事实。
5. 由有权限的责任人确认、改级或驳回，并记录理由、证据和时间戳。

现有 PR 主稿中的七因子加权公式可收敛到这四个维度：`Severity` 对应安全/监管影响，`Potential Reach` 和 `Brand Proximity` 对应影响范围，`Source Authority` 和 `Corroboration` 对应证据可信度，`Velocity` 和 `Persistence` 对应传播速度。原稿中的数值权重、分数阈值和 SLA 只视为待验证设计，不直接进入 canonical PRD。

### 5.4 P4 P0 责任与共同确认模型

产品规划层已确认采用「一个事件负责人 + 领域共同确认」：每个事件只能有一个 `incident_owner`，可以有多个 `domain_approvers`。事件负责人对流程、时间和记录完整性负责；领域确认人对专业判断负责，两者不能由系统代理。

| 角色 | P0 职责 | 权限边界 |
|---|---|---|
| PR Lead | 担任事件流程负责人，组织核验、分级、升级、更新与结案 | 不替代 Safety/Quality、Privacy/Legal 的专业判断；实际主责人与替补人待任命 |
| Safety/Quality | 共同确认产品安全、缺陷、召回及相关监管风险 | 不由模型推断医疗因果或产品安全结论 |
| Privacy/Legal | 共同确认隐私、数据、监管、claim 和评价真实性风险 | 对外法律立场、合规结论和响应内容仍按现有授权审批 |
| PR Director | 共同确认快速升级的负面舆情；作为 `Sev3/Sev4` 的 PR 侧升级角色 | 不单独替代对应领域确认人 |
| Executive Crisis Team | 接收 `Sev4` 升级并按现有危机治理机制决策 | 被通知不等于自动批准外部声明或处置动作 |

共同确认规则：

- `Sev0–Sev2`：`incident_owner` 负责分流、补证和状态维护；涉及安全、隐私、监管或法律事实的内容，在作为已确认结论使用前必须经过对应 `domain_approver`。
- `Sev3/Sev4`：PR 侧负责人和至少一名对应领域负责人共同确认等级与升级路径。一个事件命中多个风险类别时，加入所有相关 `domain_approvers`，但仍保持单一 `incident_owner`。
- `Sev4`：同步 Executive Crisis Team；具体通知渠道、响应时限和授权人待现有危机流程确认。
- 任何对外声明、媒体回复、删除请求或业务处置均走独立审批。风险分级完成不等于对外动作获批。

最小审计字段：

| 字段 | 要求 |
|---|---|
| `incident_owner` | 必填且唯一，记录角色和实际人员 |
| `domain_approvers` | 按风险类别填写，可以多人 |
| `severity_confirmed_by` | 记录确认、改级或驳回人员 |
| `approval_status` | 区分待确认、已确认、已驳回和外部动作审批状态 |
| `decision_reason` | 记录分级依据、分歧和未核验项 |
| 时间戳 | 记录分配、确认、改级、通知、升级和结案时间 |

系统可以推荐责任人、生成提醒和暴露超时，但不能自我确认风险等级、替代共同确认或绕过外部动作审批。无人接单必须显示为 `owner_unassigned`，不能自动转为已确认或已结案。

### 5.5 P4 P0 主指标

产品规划层已确认主指标为「风险确认与分级总时长」，衡量从首个可核验风险信号出现，到责任人完成人工判断与风险分级所需的时间。它衡量的是组织真正接住风险的速度，不以告警发送时间或模型自动判断时间代替。

```text
风险确认与分级总时长
  = risk_confirmed_at - source_first_seen_at
  = 系统发现耗时 + 人工确认耗时

系统发现耗时 = system_detected_at - source_first_seen_at
人工确认耗时 = risk_confirmed_at - system_detected_at
```

时间点口径：

| 时间点 | 推荐定义 | 当前状态 |
|---|---|---|
| `source_first_seen_at` | 获准监测范围内，风险信号最早可核验的原始发布时间；无法取得时使用最早可审计来源时间，并显式标注口径限制 | 数据契约待确认 |
| `system_detected_at` | 系统首次创建包含来源、证据和置信度的风险候选时间 | 产品定义已提出，待技术验证 |
| `risk_confirmed_at` | 有权限的责任人完成确认或驳回，并完成风险等级记录的时间 | 业务流程待确认 |

主指标只在已授权且覆盖状态可见的数据范围内计算。来源不可访问、限流、schema 变化、数据延迟和真实零值必须分开记录，不能把覆盖缺失计算成「没有风险」或更短的发现时长。

主指标的质量护栏：

- 高风险召回率：避免靠减少预警数量人为缩短确认时长；阈值与 gold set 待 PR、Legal/Safety/Privacy 联合确认。
- 误报率或人工驳回率：避免大量低质量候选挤占责任人处理能力。
- 证据可追溯：每个高影响风险候选必须关联原始来源、时间、引用片段和 coverage 状态。
- 人工决策边界：系统可以生成候选和建议等级，但不得自动完成危机定级、外部发布或处置动作。

目标值和各风险等级的 SLA 暂不填写。需要先用历史事件或标注样本建立 baseline，再由 PR、Legal/Safety/Privacy 和实际风险 owner 确认目标；否则任何分钟级数字都只是未经验证的假精确。

### 5.6 需要 PR 部门确认的问题

第一轮只问价值和 P0，不先谈技术：

1. 当前最痛的三项工作是什么？频率、耗时和失败代价分别是多少？
2. 首期第一目标只能选一个时，是风险提前量、媒体机会转化还是周报提效？
3. 谁是每日主用户，谁审批风险，谁审批媒体 Action，谁看管理层周报？
4. 能否提供现行周报、媒体名单、Pitch 台账和危机流程样本？
5. P0 是否接受一条纵向闭环，还是要求七个模块同时交付？

第二轮确认范围和治理：

6. PR 部门是否接受产品规划层已确认的美国市场、英语、pumping/feeding 边界？首期具体产品、SKU 和别名是什么？
7. 核心媒体和竞品首期数量是多少？
8. 已采购哪些媒体/记者数据库？保存、摘录、导出和训练权利是什么？
9. PR、Legal/Safety/Privacy 是否接受 `Sev0–Sev4` 的四维分级与共同确认模型？实际主责人、替补人、SLA、通知渠道和升级方式是什么？
10. 哪些报告、Pitch、声明、回复和内部推送必须二次审批？

第三轮确认成功与投入：

11. 当前周报工时、Pitch 回复率、风险响应和 Action 采纳 baseline 是多少？
12. 试点用户、周期、UAT 样本和 Go/No-Go 条件是什么？
13. 可投入人员、预算和采购上限是多少？
14. Action 结果由谁回填，如何连接报道、媒体回复和业务结果？

## 7. Social Intelligence：模块级完整对比

产品规划层已确认：SI P0 的唯一业务结果是「发现高价值用户痛点，并形成有证据、可审批、可回填的业务 Action」。该决定不代表社媒部门已经确认高价值标准、平台范围、Action 类型、负责人或验收口径。

| 优先序 | 模块 | 要回答的问题 | 业务价值 | 主要落地条件 | 建议阶段 |
|---:|---|---|---|---|---|
| 1 | S1 用户讨论与需求洞察 | 用户在什么场景遇到什么痛点，哪些值得业务行动 | 最直接接近真实用户问题，可用真实平台验证证据链 | 产品别名、排除词、YouTube channel/video/comment 范围、Subreddit、获准连接器、人工标注样本、痛点 taxonomy | P0；产品规划已确认，部门口径待确认 |
| 2 | Action Engine / Board | 哪些高价值痛点值得行动，由谁审批、执行和复盘 | 防止产品退化为周报生成器 | Action 类型、审批人、负责人、SLA、状态机、过期规则和任务集成 | P0 横向闭环；产品规划已确认，部门口径待确认 |
| 3 | S2 竞品社媒动作 | 竞品重点传播什么，哪些内容显著超出账号基线 | 支撑 Campaign、内容形式和差异化选题 | 官方 handle、指标快照、平台内 baseline、跨平台不可比规则 | P1 |
| 4 | S4 Creator 分析 | Creator 方向是否变化，有无竞品合作、合作时机和品牌安全风险 | 提高合作选择质量并控制披露风险 | Creator 池、CRM/合同边界、披露规则、品牌安全清单 | P1 |
| 5 | S3 趋势与内容机会 | 哪些趋势正在升温，是否适合品牌、窗口多长 | 潜在价值高，但最依赖持续时间序列和团队响应速度 | 合法趋势源、历史快照、动量算法、品牌适配规则、内容响应 SLA | P2；若业务确认趋势为第一目标则升 P1 |

推荐 P0 闭环：

```text
YouTube 获准真实数据（优先验收） ─┐
Reddit 获准真实数据（并行建设） ──┴→ Coverage 与 S1 痛点聚类
  → Evidence Gate
  → 人工确认高价值 Insight
  → 生成带 owner 与预期结果的 Action
  → 审批或驳回
  → 执行状态、结果与原因回填
```

周报、Dashboard、S2 竞品、S3 趋势、S4 Creator 和自动对外回复不进入 P0 验收。S1 中发现的安全、召回、隐私或监管事件只生成跨产品移交记录，由 PR P4 进行风险分级和危机升级；SI 不复制 PR 的 War Room。

### 7.1 SI P0 唯一业务结果

一个痛点只有同时通过证据门和人工价值判断，才成为「高价值用户痛点」。P0 不以提及量、负面情绪或模型置信度中的任何单一指标直接决定价值。

| 价值维度 | P0 判断问题 | 当前状态 |
|---|---|---|
| 用户问题强度与重复性 | 痛点造成什么具体困难或后果，是否在独立用户或场景中重复出现 | 分类规则和阈值待社媒部门确认 |
| 业务相关性 | 是否与首期市场、语言、产品/SKU、目标用户或当前业务目标直接相关 | 试点边界待确认 |
| 证据可信度 | 原始内容、时间、来源、上下文、样本和 coverage 是否足以支持结论 | Evidence Gate 设计已存在，真实数据待验证 |
| 可行动性 | 是否能形成明确 Action 类型、owner、预期结果和决策时限 | Action 类型和组织流程待确认 |

每条高价值 Insight 至少回答：目标用户是谁、发生在什么场景、具体痛点是什么、造成什么后果、有哪些支持与反证、覆盖缺口是什么，以及为什么值得现在处理。每条候选 Action 必须引用 `insight_id` 和 `evidence_set_id`，包含 Action 类型、owner、预期结果、审批状态、有效期和结果回填字段。

P0 完成不等于系统生成了周报，也不等于生成了大量 Insight。只有真实数据形成高价值痛点、经人工确认后转为待审批 Action，并能记录审批与执行结果，才算跑通业务闭环。

### 7.2 SI P0 平台顺序与已有资产

产品规划层已确认：YouTube 是 P0 主线和优先验收路径，Reddit 与 YouTube 同期建设。Reddit 不是 YouTube 的替代源，也不延后到 P1；两个平台分别报告 coverage、错误和验收结果，不能直接比较绝对提及量。

2026-08-14 定向 Deep Research 结论：YouTube P0 应采用官方 YouTube Data API 为主源，以固定频道 uploads playlist 为稳定范围、有限关键词搜索为发现补充，使用 `commentThreads.list` 获取评论线程，并在需要完整上下文时用 `comments.list` 补齐回复。现有本地 Apify 采集器只证明视频发现，不具备 S1 所需的评论正文、线程和回复；且供应商来源方式、YouTube 抓取政策与合同权利尚未通过审查，不能作为 P0 主线。完整证据、路径比较、数据契约和门槛见 [`YouTube P0 定向 Deep Research 与数据契约建议`](2026-08-14_YouTube_P0定向DeepResearch与数据契约建议.md)。

执行顺序：

1. 优先完成 YouTube 官方 API 项目和 Analytics & Reporting / derived metrics 合规门，随后完成评论级真实连接、视频范围、分页/回复、CanonicalMention、Evidence、Coverage、30 天刷新/删除和 S1 → Action 端到端验收。
2. Reddit 并行复用已有工作台和已完成能力，补齐与 canonical 数据契约的映射及独立验收。
3. 两个平台共用 Insight、Evidence 和 Action 语义，但保留平台能力差异，不用一方缺失字段伪造另一方字段。
4. YouTube 主线失败不能由 Reddit 数据替代为「YouTube 已通过」；Reddit 并行链路延误或平台特有缺陷不阻塞 YouTube 的产品级 Go/No-Go。

Go/No-Go 规则：

| 验收对象 | 通过条件 | 失败影响 |
|---|---|---|
| YouTube 主线 | 官方 API 与准确的评论 NLP/痛点聚类用例获准；评论级真实数据完成分页、回复 coverage、生命周期，并跑通 Coverage → S1 → Evidence → 人工确认 → Action → 结果回填 | SI P0 产品级 No-Go；Reddit 通过不能替代 |

| 共享底座 | CanonicalMention、Evidence、Coverage、Action 和审批语义在两条链路保持一致 | 如果缺陷破坏 YouTube 端到端闭环，则阻塞产品级 Go/No-Go；仅影响 Reddit 的适配缺陷不阻塞 YouTube |

## 8. Canonical PRD 合并方案

### 8.1 PR canonical 文档体系

不建议把所有内容合成一篇巨型文档。采用四层单一事实源：

| 层级 | 主文档 | 内容 |
|---|---|---|
| 业务需求与决策 | 本文后续确认版或独立业务需求文档 | P1–P6、优先级、RACI、baseline、P0、Go/No-Go |
| 研发 PRD | PR-PRD | 功能、状态、数据契约、错误、输出、验收 |
| 研究附录 | PR-PPLX + PR-IMP 中的外部研究 | 带来源和 `verified_at` 的媒体、竞品、监管、供应商事实 |
| 决策日志 | `work_log/` | 方案选择、权重、未知项、变更原因和签字状态 |

PR canonical 处理：

- 保留 PR-PRD 的产品结构、数据契约、证据门、技术边界和验收。
- 吸收 PR-IMP 的业务问题、反证、rights matrix、RACI、12 周路线和 Definition of Done。
- 将 PR-PPLX 的外部研究降级为带时间戳附录。

- 删除 P0 Milvus、固定 GPT-4o、知识图谱、未经授权 Reddit 和自动外发承诺。
- 风险统一采用 Sev0–Sev4；风险分和 Confidence 分开显示。

## 10. Deep Research 决策规则

满足任一条件时，才触发定向 Deep Research：

- 候选方案基准分差小于 5 分，且外部事实可能改变选择。
- 权重敏感性出现赢家翻转或最差领先不足 3 分。
- 权重不低于 15% 的维度只有 C/D/U 证据。
- 硬门槛取决于外部 API、供应商授权、平台政策、字段覆盖、价格或合规解释。
- 候选对同一外部事实给出矛盾结论。
- build/buy 或供应商选择可能形成明显锁定和高返工。
- 需要行业指标、基线或案例，但内部无历史数据。

不应通过 Deep Research 回答：

- 部门真实目标和优先级。
- 谁负责审批、执行和复盘。
- 团队是否愿意采用。
- Momcozy 已有哪些账号、合同和内部数据。
- 一次真实 API 技术验证就能回答的问题。

定向研究立项前必须填写：
