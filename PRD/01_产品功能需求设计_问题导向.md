# 产品功能需求设计（问题导向）

> 版本：v1.0 | 日期：2026-08-13
> 阶段：**PRD 可行性打磨与验证**（不进入实现，不写采集器/建表/生成器）
> 目标：把 PR 团队与社媒团队的需求原话，转成一套可验证的「问题 → 数据 → 分析对象 → 结论 → 产品形态」链条

---

## 一、定位与阶段边界

**当前唯一目标**：验证 PRD 可行性，回答 5 个问题：
1. 要解决什么问题（要回答哪些业务问题）
2. 要抓取什么数据（每个平台是否有稳定采集方法）
3. 要分析什么对象（实体与关系）
4. 要得出什么结论（交付物与可验证指标）
5. 要交付什么产品形态（网站 + 关联 Agent）

**明确不做**（本阶段）：不写新采集器、不建新表、不写周报生成器、不做前端页面、不做飞书集成。上一步审计中「合规路线切换」「schema 落库」等改进项，凡涉及代码实现的，一律暂缓，只在本设计里以「待确认/设计决策」形式记录。

**上一步审计的承接**：三条改进已在设计层落实——①数据源采用「第一梯队 Apify/TikHub + 第二梯队 GitHub 兜底」双轨制（替代原先单一灰色路径）；②竞品词典收敛为单一分析对象（见第三节）；③结论层补 outcome 指标（见第五节）。其余改进项超出本阶段范畴，暂缓。

## 二、需求 → 问题（问题导向，这是本设计的核心）

### 2.1 PR 团队：六个业务场景 → 要回答的问题

> 来源：`PR/momcozy-pr-intelligence-ai-agent-plan.ds.md` + 跨境 PR 文章（Earned Media 逻辑）

| # | 业务场景 | 要回答的问题 |
|---|---------|------------|
| P1 | 品牌声誉健康度 | 本周 Momcozy 的媒体声量与情感趋势如何？核心信息（Comfortable/Hands-Free/FDA Cleared/Science-backed）在媒体中的渗透率是多少？ |
| P2 | 竞品攻防卡位 | 竞品（Elvie/Willow/Medela/eufy/Spectra 等）本周有哪些新品、融资、测评、召回动态？哪里存在 Momcozy 缺位的「横评」真空区？ |
| P3 | 媒体关系与 Pitch | 核心编辑（Wirecutter/Parents/What to Expect/BabyGearLab 等）最近关注什么选题？何时、以什么角度 Pitch Momcozy 成功率最高？ |
| P4 | 危机预警 | 有没有从论坛/社媒向主流媒体发酵的负面信号？监管（FDA/CPSC/Health Canada/召回）有没有 Momcozy 或竞品相关的动态？ |
| P5 | 议题设定 | 行业升温话题（职场泵奶权、产后心理健康、FemTech 等）里，哪些值得 Momcozy 发声、用什么叙事切入？ |
| P6 | 战略决策 | 进入新市场前，当地媒体对「可穿戴吸奶器」品类的态度和关键议题是什么？ |

**PR 交付物**：每周 PR Intelligence Report + P0/P1 实时预警 + 可执行的 PR Actions（Pitch / Seeding / 风险干预）。

### 2.2 社媒团队：四个模块 → 要回答的问题

> 来源：`VR/PRD-Momcozy-Social-Intelligence-Agent.md` + 用户提供的需求原话

| # | 模块 | 要回答的问题 |
|---|------|------------|
| S1 | 用户讨论洞察 | 用户最近在社媒上讨论什么？最关注哪些问题？有哪些新需求、痛点、内容机会或潜在风险？哪些话题热度正在上升？ |
| S2 | 竞品社媒监控 | 竞品最近重点推广什么？采取了哪些营销动作（Campaign/新品/节点/Creator 合作/UGC）？哪些内容表现突出？对我们的内容策略有什么启发？ |
| S3 | 热点趋势洞察 | 最近哪些 Hashtag/BGM/内容模板在升温？哪些与母婴或目标人群相关？品牌是否适合参与、从什么角度切入、时间窗口是什么？ |
| S4 | Creator 分析 | 重点 Creator 最近在关注和创作什么？哪些内容方向表现好？受众关注什么？有没有内容或合作机会？ |

**社媒交付物**：每周 Social Media Intelligence Report + 可执行的 Social Media Actions。

### 2.3 两团队的共同第一性需求

周报 + P0 预警只是**载体**，不是**目的**。真正的第一性需求是：
- **缩短「信号 → 决策」的时间**（风险提前量、趋势参与时效）
- **让洞察可执行、可追溯**（每条结论带证据，每个 Action 带责任人/时间窗/验收指标）
- **建立品牌知识资产**（竞品词典、话题、Creator、行动结果可积累复用）

## 三、要抓取的数据（数据源矩阵：双轨制）

### 3.1 采集优先级（用户指定，本设计固化）

**第一梯队（已有 API Key，每个平台必须跑通稳定采集）**：
- Apify：https://apify.com/store
- TikHub：https://user.tikhub.io/dashboard/api-marketplace

**第二梯队（主动 + 兜底 + 适配性）**：
- https://github.com/stars/zjgulai/lists/data-achieve（19 个仓库）

### 3.2 平台 × 数据源矩阵（第一梯队为主，第二梯队兜底）

| 平台 | 第一梯队：TikHub 端点 | 第一梯队：Apify Actor | 第二梯队：GitHub 兜底 | 当前状态 |
|------|----------------------|----------------------|----------------------|---------|
| **Reddit**（重点） | `/api/v1/reddit/app/fetch_dynamic_search`（关键词+subreddit 搜索） | `apify/reddit-scraper` | `Agent-Reach`（零 API 费 Reddit 阅读器） | ✅ LIVE（67 条已验证） |
| **TikTok** | `/api/v1/tiktok/web/user/posts`（竞品账号）、`/web/hashtag/videos`、`/web/explore/trending`、`/app/v3/fetch_creator_search_insights_videos`（搜索） | `clockworks/tiktok-scraper` | `TikHub-API-Python-SDK`（官方 SDK，替换手写 httpx） | ✅ LIVE（30 条已验证） |
| **Instagram** | `/api/v1/instagram/web/get_user_info_and_media_v2`（账号）、`/web/hashtag`、`/web/search_reels` | `apify/instagram-scraper` | `browser-use`（登录态浏览器自动化） | ⚠️ CODE_UNVERIFIED |
| **YouTube** | `/api/v1/youtube/web/search_video` | `apify/youtube-scraper` | 官方 YouTube Data API v3（合规首选）+ `Agent-Reach` | ⚠️ CODE_UNVERIFIED |
| **Facebook Pages** | —（TikHub 无 FB 主页能力） | `apify/facebook-posts-scraper`（代码已引用 `apify~facebook-posts-scraper`） | `browser-use` | ⚠️ CODE_UNVERIFIED（需 Apify Key） |
| **Facebook Groups**（重点） | — | `apify/facebook-groups-scraper` | `browser-use` / `browser-harness`（登录态） | ❌ 未写（合规待确认） |
| 监管源 RSS | —（免费，直接 HTTP） | — | — | ⚠️ CODE_UNVERIFIED（URL 待验证） |
| 媒体 RSS | —（免费，直接 HTTP） | — | — | ⚠️ CODE_UNVERIFIED |

### 3.3 第二梯队仓库适配性判定（data-achieve 列表）

| 仓库 | 适配场景 | 优先级 |
|------|---------|--------|
| `TikHub/TikHub-API-Python-SDK` | 第一梯队 TikHub 的官方 SDK，替换现有手写 `httpx` 调用，提升稳定性 | 高 |
| `Panniantong/Agent-Reach`（71k⭐） | Reddit/Twitter/YouTube/GitHub 零 API 费阅读器，Reddit/YouTube 兜底 | 高 |
| `browser-use/browser-use`（108k⭐）+ `browser-harness` | Facebook Groups / Instagram 登录态浏览器自动化，合规兜底 | 中 |
| `firecrawl/firecrawl`（166k⭐） | 通用网页抓取，媒体正文/编辑档案兜底 | 中 |
| `KnockOutEZ/wigolo` | 本地 MCP 抓取，无 API 费 | 低 |
| 其余（sherlock/maigret/autoscraper/spiderfoot 等） | OSINT 泛用，与本项目核心需求弱相关 | 暂不采用 |

### 3.4 稳定性要求（「每个平台都要稳定采集」的验收标准）

1. **双源可切换**：每个平台至少有一个「第一梯队主源 + 一个第二梯队兜底」，主源失败自动降级，不出现单点。
2. **幂等 + 游标**：所有采集器以 `platform + item_id` 为唯一键，可重复运行不重复入库。
3. **覆盖率诚实表达**：缺失字段记为 `null`（不是 0），报告里明确「已覆盖范围」而非「全平台」。
4. **失败可观测**：401/429/schema 变化/空结果分别记录，不把「抓不到」写成「没有」。

## 四、要分析的对象（实体与关系）

### 4.1 六类实体

| 实体 | 说明 | 单一真源 |
|------|------|---------|
| 品牌实体 | Momcozy + 产品型号（M5/BP380、M9/BP223、V1 Pro 等）+ 用户俗称 + 拼写变体 | `dim_product_alias`（PRD 已定义） |
| 竞品实体 | 21+ 品牌 + 核心型号 + 各平台官方账号 handle | **竞品维度表 v1.1（收敛为唯一词典）** |
| 内容对象 | post/video/comment/article，统一为 CanonicalMention（provider + provider_item_id + source_url + published_at + collected_at） | `dwd_canonical_mention` |
| 作者/Creator | 内容作者、KOL，含 follower_tier、内容方向、商业披露 | `dim_creator` |
| 媒体/记者 | 核心媒体 + 编辑（beat、偏好、pitch 历史、冷却期） | `dim_media_contacts` |
| 话题/趋势 | 话题聚类 + 趋势实体（hashtag/BGM/模板）+ 动量 | `dim_topic` / `dws_trend_snapshot` |

### 4.2 关键关系（分析的价值来自关系，不是单条数据）

```
内容 --提及--> 品牌/竞品/产品型号
内容 --归属--> 平台 --能力--> 连接器（字段/权限/延迟/覆盖缺口）
Creator --合作--> 竞品（#ad/#sponsored/商业披露）
媒体/记者 --发布--> 文章 --关联--> 选题趋势
洞察 --引用--> 证据集(evidence_set) --指向--> 原始内容
Action --来源于--> 洞察 --引用--> 证据集
```

**核心设计原则**（来自 PRD + AMEC）：事实、推断、判断三者分离保存，每条结论带 `evidence_set_id` + `model_version` + `coverage`，AI 生成内容永远是人类审批前的「草稿」。

## 五、要得出的结论（交付物 + 可验证指标）

### 5.1 三类交付物

| 交付物 | 频率 | 内容 |
|--------|------|------|
| PR Intelligence Report | 每周一 | 执行摘要 + P0/P1 预警 + 媒体/竞品动态 + 机会清单 + PR Actions + 上周跟进 |
| Social Media Intelligence Report | 每周一 | 执行摘要 + S1 用户讨论 + S2 竞品动态 + S3 趋势 + S4 Creator + Social Actions |
| P0 实时预警 | 触发即推 | Sev4 15 分钟 / Sev3 60 分钟，含原文 + 风险评级 + 建议回应口径 |

### 5.2 可验证指标（outcome 层，不是 output 层）

> 对齐 AMEC Barcelona Principles 4.0：反对 vanity metrics（覆盖量/likes），要求测「态度与行为改变」。

| 指标 | 定义 | 当前基线 | 目标 |
|------|------|---------|------|
| 风险提前量 | 风险首现 → PR 确认的时间 | 未测量 | P0 <4h，P1 <24h |
| Pitch 成功率 | 基于系统建议的 pitch 回复率 vs 历史 | 未测量（需先建 3 个月基线） | 建议 pitch 回复率 > 基线 1.5 倍 |
| 趋势参与时效 | 趋势识别 → 品牌发布内容的时间 | 未测量 | 高热趋势 72h 内 |
| 覆盖完整度 | 采集到的竞品内容 / 竞品实际发布 | TikTok ~70%，其他 0% | 三平台 >85% |
| 周报生产效率 | 数据冻结 → 周报发布的人工工时 | 3-5h（手工） | <60min（审核+修改） |
| Action 采纳率 | 系统建议被团队执行的比例 | 未测量 | 首月 ≥50% 建议被采纳 |

### 5.3 行业标准对标（深度调研结论）

| 案例 | 可借鉴的标准做法 |
|------|-----------------|
| **IKEA + Sprinklr** | Media Impact Score 五指标：Relevance / Engagement / Domain Authority / Global Rank / Syndication —— 与现有权重体系（S/R/B/T/K 五维）思路一致，可校准权重 |
| **Samsonite + Onclusive** | 「信号 vs 噪音」：5 万月提及里绝大多数是促销噪音；分层报告节奏：日报（客服）/ 周报（领导）/ 月报（营销产品）/ 季报（战略） |
| **HelloFresh + Talkwalker** | 实时告警只看「高触达负面提及」，避免告警疲劳；结果多发现 400% 提及 |
| **KIKO + Launchmetrics** | 单一真源（single source of truth）+ MIV 统一度量 + 竞品 benchmark |
| **Søstrene Grene + Meltwater** | 媒体监测与「记者发现」合一：关键词 → 提及 + 记者/意见领袖识别 |

## 六、要交付的产品形态（网站 + 关联 Agent）

### 6.1 网站（Web Dashboard，Next.js 复用现有 app/dashboard）

```
┌─────────────────────────────────────────────────────┐
│  产品：Momcozy Intelligence（网站 + 关联 Agent）       │
├─────────────────────────────────────────────────────┤
│  1. 概览 Overview：今日重要信号 / 声量情感趋势 /       │
│     竞品动态 / 待处理 Action / 数据覆盖状态横幅        │
│  2. 品牌与竞品：竞品雷达图 / 核心信息渗透率 / 横评缺口 │
│  3. 媒体中心：核心媒体瀑布流 / 编辑档案卡 / Pitch 建议 │
│  4. 社媒洞察：S1 用户话题 / S2 竞品内容 / S3 趋势雷达  │
│     / S4 Creator 时间线                               │
│  5. 信号 & 行动中心：类 Trello 看板（发现的机会/        │
│     确认的风险/已执行行动），支持拖拽更新状态            │
│  6. 报告生成器：自定义时间/专题，一键导出 Markdown      │
│  7. Admin：监测范围 / 连接器与授权 / 词典 / 告警规则    │
└─────────────────────────────────────────────────────┘
```

**信息架构铁律**（来自 PRD）：
- 主界面先展示「重要信号 + 数据覆盖状态」，不先铺数据墙
- 每条洞察可点击展开证据链（原文 + 时间 + 平台 + 样本量 + 置信度）
- 「结论—证据—决策—结果」一体化，覆盖缺口必须可见

### 6.2 关联 Agent（多智能体，LangGraph 编排）

```
监测 Agent（数据采集 + 清洗 + 实体抽取）
    ↓
分析 Agent（话题/情感/趋势/竞品动作/Creator 分析）
    ↓
策略 Agent（交叉比对 → 生成 Action 候选 + "为什么这么做"）
    ↓
报告 Agent（融合为 Markdown 周报草稿）
    ↓
证据问答 Agent（"Ask Momcozy Intelligence"：问答带证据引用）
```

**Agent 铁律**：检索/指标/证据门（evidence gate）用工具返回结构化数据，不交给 LLM 自由发挥；所有外部动作（发帖/联系记者/联系 Creator）必须 human-in-the-loop，AI 只产出「待审批草稿」。

## 七、PRD 可行性验证清单（本阶段要确认的事）

| # | 待验证项 | 验证方式 | 影响 |
|---|---------|---------|------|
| 1 | 每个平台的稳定采集方法（第一梯队） | 在真实环境跑通 6 个平台各取 ≥5 条数据 | 决定数据源矩阵是否成立 |
| 2 | Facebook Groups 的 Apify actor 可用性与 ToS 风险 | 跑一次 + 法务确认 | 决定 S1 重点平台能否覆盖 |
| 3 | 监管/媒体 RSS URL 有效性 | 服务器 `--dry-run` | 决定 P0 预警地基 |
| 4 | 竞品词典（21 品牌 + 型号 + handle）业务最终确认 | 与业务对齐 | 决定采集配置唯一真源 |
| 5 | 周报语言（中/英）与接收人 | 与 PR/社媒团队确认 | 决定 LLM prompt 与报告结构 |
| 6 | 是否已有 Meltwater/Cision 等工具在并行使用 | 业务调研 | 避免重复建设 |

## 八、明确不做（边界，防止范围蔓延）

- ❌ AI 自动发送 pitch 邮件 / 自动发布内容 / 自动联系 Creator / 自动 @ 媒体
- ❌ 采集私密群组、绕过登录墙、绕过验证码
- ❌ 把「抓不到」写成 0，或把「全平台」当成默认覆盖
- ❌ 把 LLM 生成的推断当成事实对外发布（必须 Analyst 审批）
- ❌ 本阶段进入代码实现（采集器/建表/生成器/前端全部延后到 PRD 验证通过后）
