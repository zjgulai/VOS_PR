# Momcozy Social Intelligence Agent PRD v2

> 版本：v2.0（deep research 重写版）
> 文档状态：待业务评审
> 文档日期：2026-08-13
> 目标团队：Momcozy 社媒团队、内容团队、Creator 合作团队、品牌与产品团队、数据与研发团队
> 核心逻辑：Social Monitoring → Insights → Trend & Content Intelligence → Social Media Actions
> 研究口径：英文优先检索；平台能力以官方文档与合规实践为准；无法确认的内容标记为「未验证」或「此处未解决」

## AI 速读卡

- 产品一句话：把跨平台公开社媒信号变成可追溯的母婴用户洞察、竞品判断、趋势机会和待审批社媒行动。
- 核心循环：配置监测范围 → 采集 → 标准化与质量检查 → AI 分析 → 证据核验 → Action 审批 → 记录结果。
- 四大洞察模块：S1 用户讨论与需求洞察、S2 竞品社媒动作监控、S3 热点与内容趋势、S4 重点 Creator 分析。
- 目标平台：Reddit（重点）、Facebook Groups（重点）、Instagram、Facebook Pages、YouTube、TikTok；接入按平台能力矩阵分阶段交付。
- 硬约束：不绕过登录、权限、验证码或平台限制；每条结论必须能回溯到来源和采集时间；AI 不自动对外发帖、联系 Creator 或发布内容。
- 推荐默认：先用 Reddit、YouTube 和品牌自有账号验证闭环；Meta/TikTok 外部监听采用 Apify/TikHub licensed provider 连接器。
- 发挥空间：看板视觉、报告版式、模型供应商、队列和云厂商可以替换，但不能破坏数据契约和证据链。
- P0 验收：社媒分析师能配置一个监测任务，得到带来源证据的周报，并把一条建议转为可跟踪 Action。
- 最容易翻车：把抓取延迟当作实时数据、把单条低置信度帖子当作趋势、把模型猜测写成事实、让 Agent 自动对外联系 Creator 或发布内容。
- 超预期机会：需求到内容机会图谱、Creator 合作时机卡、行动结果反哺模型评估集、竞品 Campaign 解码卡。


## 第一章：产品概述

### 1.1 产品定位

Momcozy Social Intelligence Agent 是一款面向跨境母婴品牌的社媒情报与行动决策产品，让社媒团队能够持续发现用户需求、竞品动作、内容趋势和 Creator 机会，并在每个结论后看到证据与不确定性，而无需手工浏览多个平台、复制数据和拼接周报。

系统不等于一个「社媒内容爬虫」，也不等于一个只会生成摘要的聊天机器人。它必须完成五段闭环：

```text
监测范围与数据源配置
        |
        v
平台连接器与采集任务（Reddit / YouTube / Meta / TikTok）
        |
        v
标准化 CanonicalMention / Content / Creator / Metric Snapshot
        |
        v
话题聚类 / 需求分析 / 情感标注 / 竞品动作 / 趋势识别 / Creator 画像
        |
        v
Evidence-backed Insight（含证据集、置信度、覆盖说明）
        |
        v
Social Media Action → 人工审批 → 执行 → 结果记录 → 复盘反馈
```

### 1.2 业务目标与问题定义

#### 1.2.1 业务目标

| 目标 | 结果定义 | 首期衡量方式 |
|---|---|---|
| 缩短信息发现时间 | 分析师从「浏览平台」转为「审核已筛选证据」 | 基线周与上线后周的人工监测工时对比 |
| 提高洞察可执行性 | 每个重要洞察都带建议动作、负责人角色、平台、时间窗和证据 | Action 完整率、采纳率、完成率 |
| 降低误判风险 | 区分采集事实、模型推断、人工判断和未知项 | 证据覆盖率、人工驳回率、抽检错误率 |
| 形成品牌知识资产 | 关键词、产品别名、话题、Creator、竞品动作和行动结果可积累 | 词典版本数、洞察复用率、行动复盘数量 |
| 支撑内容与 Creator 协同 | 将用户痛点映射到内容机会、FAQ、产品反馈和 Creator brief | 洞察被内容团队采用的数量 |

#### 1.2.2 业务问题

| 问题 | 需要回答的问题 | 产出 |
|---|---|---|
| 用户讨论分散 | 用户最近在讨论什么、为什么讨论、哪里变热 | Social Listening Brief |
| 产品需求隐藏在评论中 | 用户的真实使用场景、疑问、痛点、正负面反馈是什么 | Need / Pain / Question Cards |
| 竞品动作不透明 | 竞品在推广什么、用什么内容形式、哪些内容明显跑出基线 | Competitor Intelligence Cards |
| 热点难以判断是否适合品牌 | 热度是真是假、是否与目标人群相关、何时参与、怎么切入 | Trend Opportunity Cards |
| Creator 只看粉丝数 | Creator 最近关注什么、受众回应什么、是否处于合适合作窗口 | Creator Intelligence Cards |
| 洞察不能落地 | 哪些话题值得回应、哪些内容值得做、谁负责、何时完成 | Social Action Board |

### 1.3 Momcozy 社媒业务上下文

#### 1.3.1 品牌社媒现状基线

Momcozy 官网当前公开的业务分类包括 Pregnancy、Bras and Postpartum、Pumping、Feeding、On The Go、Baby Care 等，产品覆盖可穿戴吸奶器（M5/BP380、M9/BP223、V1 Pro、Air 1、W1）、哺乳文胸、喂养电器（KleanPal Pro）、婴儿背带、婴儿监视器等多品类。从品牌社媒声量的公开信号来看，当前可观察到以下基线方向：

**TikTok / Instagram / YouTube 内容基线**：Momcozy 官方账号主要围绕可穿戴吸奶器的使用场景（工作、旅行、日常、通勤）生产 POV 和 unboxing 内容，整体策略倾向于真实用户故事和功能演示。Mother's Day、Back-to-Work 等节点是历史上互动较高的内容窗口。然而，品牌的内容在三平台上均未建立可与 Elvie、Eufy 同等级别的内容差异化叙事：Elvie 围绕「FemTech 领导者 + 设计美学」、Eufy 围绕「智能加热 + 产出量」形成了更清晰的内容 identity，而 Momcozy 目前的内容定位在「性价比 + 多选择」之间摇摆，未能在社媒层建立稳定的记忆符号。

**Reddit 和 Facebook Groups 的讨论特征**：Reddit 的 r/breastfeeding、r/NewParents、r/beyondthebump 以及母婴 Facebook Groups 是真实用户讨论最集中的非品牌控制场。这些社区的讨论特点是：高信息密度（用户会详细描述使用场景、型号对比、测量结果）、高真实性（匿名和社区压力共同减少了品牌软文）、高价值信号（出现「我换掉 Momcozy 换了什么」「Momcozy M9 vs Willow」这类对比讨论，直接揭示产品定位缺口）。这是系统 S1 模块的核心价值场景：系统性地将分散在数百个帖子里的用户讨论聚类为可行动的需求信号。

**Creator 生态现状**：母婴垂类 Creator 在 TikTok 和 Instagram 上可大致分为三类——哺乳 / 泵奶专注型（通常是 IBCLC 认证或有明确泌乳经验）、新手妈妈日常 vlog 型（产后生活、工作与育儿平衡）、Baby Gear 测评型（系统评测、对比型内容）。Momcozy 在历史上以 seeding 为主，与大量中小 Creator 合作，但公开披露的 #ad 内容较为密集，Reddit 社区已出现对「Momcozy 是否找了大量 PR Creator」的讨论。这意味着系统 S4 模块的 Creator 分析不仅要识别合作机会，还要监控商业披露合规和受众对品牌 Creator 内容的反应情绪。

#### 1.3.2 竞品社媒动作基线

母婴吸奶器赛道竞品的社媒策略可观察到以下差异化打法：

- **Elvie / Willow（合并后）**：主打 FemTech 身份认同叙事，内容围绕「现代女性选择」而非纯粹的产品功能，在 LinkedIn 和 Instagram 上强调品牌声誉和医疗专业支持。Creator 合作选择更聚焦在专业形象强的创作者（IBCLC、产科医生背景）。
- **Eufy**：近两年在 TikTok 上快速增长，内容策略以「开箱 + 实测 + 数据展示（oz/产出量）」为核心，利用具体数据可视化建立「高效能」心智。其在 YouTube Shorts 的布局形成了对 Momcozy 的正面竞争。
- **Medela**：传统品牌在社媒上保持教育性内容策略（泵奶指导、正确配件使用），而非追逐潮流，受众偏向信任已建立的品牌。
- **Haakaa / Frida**：专注在「低干预、自然、便携」的生活方式定位，内容更接近生活方式博主而非产品营销，产生了较高的社区归属感内容。

这一竞品格局的含义：Momcozy 的社媒内容策略如果只停留在功能展示和性价比叙事，在 S2 模块中将持续看到竞品在情感连接和专业信任维度的领先。系统需要帮助团队识别竞品正在投入的内容形式和主题，以便做出差异化决策。

#### 1.3.3 行业风险信号

从公开可观察的信号来看，社媒层存在以下需要持续监测的风险：

1. **虚假评价与隐性营销质疑**：Reddit 社区出现过对 Momcozy Creator 合作密度的质疑（「是否所有正面评价都是 PR 产品？」），属于未经证实但重复出现的信号。FTC 自 2024-10 实施消费者评价与推荐规则，Creator 合作的披露要求已是法律议题，不仅仅是公关风险。系统 S4 模块必须把 `disclosure_check` 设计为 Creator 合作卡的必填字段。
2. **产品安全舆情扩散路径**：公开信息显示（来源：ClassAction.org）KleanPal Pro 存在集体诉讼信号，Reddit 是此类话题从小圈子扩散到主流媒体的中转站。系统需要监测产品安全相关关键词在 Reddit 和 Facebook Groups 的早期讨论，建立「社媒层 → PR 预警」的风险传递机制。
3. **母婴内容平台敏感性**：TikTok 和 Instagram 对涉及婴儿安全、哺乳、孕产健康的内容有更严格的平台规则，竞品的某些内容形式（如宣称特定产奶量的视频）可能在平台政策收紧时面临下架风险。系统需要监测竞品内容是否触碰平台规则，以便 Momcozy 在竞品被下架时做出快速内容布局。

### 1.4 三类用户画像

| 角色 | 核心目标 | 对现有工具最大的不满 | 愿意切换的功能 |
|---|---|---|---|
| 社媒分析师 | 每日发现重要话题，产出周报与风险提示 | 数据散落，手工复制链接，无法判断热度是否真实 | 点击洞察即可展开原文、时间、平台、样本量、置信度和证据链 |
| 内容与 Creator 负责人 | 找到可执行选题、内容形式和合作对象 | 竞品和热点信息无法转成 brief，Creator 只按粉丝量排序 | 一键生成带角度、平台、时间窗、风险和素材要求的 Action/brief |
| 品牌、产品与管理者 | 判断舆情、竞品和机会是否值得投入 | 看到了结论却不知道来源、数据完整度和建议依据 | 「结论—证据—决策—结果」一体化摘要，支持审批和复盘 |

### 1.6 可行性边界

| 在范围内及原因 | 明确排除在外及原因 |
|---|---|
| 采集公开内容、品牌自有账号数据、获得授权的 Page/Business 数据和 licensed provider 数据 | 绕过登录、验证码、访问控制、地区限制或平台反自动化机制 |
| Reddit 公开帖子、评论、Subreddit 上下文和允许使用的指标（Apify/TikHub actor 已验证） | 把 Reddit 历史全量 firehose 当作默认能力；历史覆盖必须以实际授权和连接器说明为准 |
| YouTube 公开视频、频道、视频统计和公开评论线程（官方 Data API v3） | 把 search.list 结果总数当作精确市场规模；官方文档明确总数可能是近似值 |
| TikTok 公开内容通过 TikHub API（已有 API Key）的合规接入 | 把 TikTok Research Tools 作为商业监听默认入口；官方定位面向符合条件的非商业研究者 |
| 已完成 Meta 审核和授权的自有 Page、Instagram Business 数据 | 未经确认的 Facebook Groups 全量监听，尤其是私密群组和成员画像 |
| 对视频做平台允许的字幕、标题、描述、评论和元数据分析 | 未获授权下载、长期保存或再发布完整视频、音频或用户个人资料 |
| Markdown、JSON、CSV 报告和内部 Action/brief | AI 自动代表 Momcozy 对外回复、发帖、投放广告或联系 Creator |

### 1.7 约束分层

| 硬约束 | 推荐默认 | 发挥空间 |
|---|---|---|
| 所有外部数据必须有 provider、source_url 或 provider_item_id、published_at、collected_at 和数据能力标签 | 先建立 Reddit、YouTube、品牌自有 Meta 数据和可人工导入数据的闭环 | 可用 Metabase、内置看板或现有 Next.js 看板呈现 |
| 不采集私密群组、未授权账号和平台明确禁止的内容；AI 生成内容不自动对外发布 | 连接器采用统一接口，平台差异放在 adapter 内 | 队列可用 Redis、SQS、Pub/Sub 或现有任务调度器 |
| 重要结论必须引用至少一条证据，趋势和风险结论需要多条独立证据或标记低置信度 | 原文存在对象存储或本地原始归档，分析层只引用 evidence_id | LLM 可用已批准的 Kimi、DeepSeek、Claude、OpenAI 或云上模型 |
| 删除、下架和合规请求必须能按 provider_item_id 定位并清理 | 原始数据与派生数据分开，保留删除审计记录 | 归档周期和跨区域部署由法务与基础设施团队决定 |
| FTC Creator 披露规则：涉及金钱、赠品或物质关系的推荐必须清晰披露；合作建议必须包含 disclosure_check | 商业披露检测（#ad/#sponsored/#gifted/paid partnership）作为 Creator 合作卡必填字段 | 披露检测规则可按平台和地区扩展 |

```text
+----------------------------------------------------------------------------+
```

#### b) 交互流程

正常流程：

```text
Admin 选择新增监测对象
  --> 选择对象类型：品牌 / 产品 / 话题 / 竞品账号 / Creator 账号 / 社区
  --> 输入标准名称、别名（BP编码）、排除词、语言、地区
  --> 系统预览匹配规则和可能误匹配样本
  --> 选择连接器（TikHub / Apify / Agent-Reach 兜底）和采集频率
  --> 运行连接测试，返回能力矩阵（字段 / 权限 / 估计延迟）
  --> 保存配置版本
  --> 调度器在下一周期使用新版本
```

失败流程一：连接凭证过期或配额耗尽。

```text
测试连接
  --> provider 返回 401 或 429
  --> 状态变为「待授权」或「配额耗尽」，隐藏原 token
  --> 展示重新授权入口和影响范围（哪些监测任务受影响）
  --> 不删除历史数据，不继续重试无效请求
  --> 系统记录降级时间，报告显示该平台数据缺口
```

失败流程二：平台能访问但字段不完整。

```text
测试连接
  --> 返回内容但缺少评论数、互动量或历史快照
  --> 创建 coverage_gap 记录，标记缺失字段
  --> 连接器标记为「部分可用」
  --> 报告显示字段缺口说明，禁止把缺失值当作 0
```

失败流程三：监测词命中大量噪声。

```text
预览匹配
  --> 噪声样本（无关产品名、同名词等）比例超过配置阈值（默认 40%）
  --> 系统提示添加上下文词或排除词
  --> 允许保存为观察任务，但默认不触发 Action 生成
  --> 展示 3-5 条样本让 Admin 人工判断
```

#### c) 状态清单

| 状态名称 | 触发条件 | 视觉标识 | 退出条件 |
|---|---|---|---|
| 草稿 | 新配置未保存 | 灰色 Draft | 保存或放弃 |
| 已启用 | 配置保存且连接测试通过 | 绿色 Enabled | 停用、授权失效或质量失败 |
| 部分可用 | 只能获取部分字段或覆盖有限 | 黄色 Partial | 字段恢复或 Admin 确认继续使用 |
| 待授权 | 凭证缺失、过期或平台审核未通过 | 橙色 Action needed | 完成授权并测试通过 |
| 合规确认中 | 平台（如 FB Groups）需要法务确认 | 蓝色 Pending review | 法务确认通过或明确排除 |

| 质量异常 | 连续运行无数据、重复率异常或 schema 变化 | 红色 Quality issue | 修复连接器并通过回归样本 |

#### b) 交互流程

正常流程：

```text
用户选择时间范围、平台、品类或产品型号
  --> 系统读取 DWD canonical mentions 和 metric snapshots
  --> 过滤低质量（机器人、重复、促销噪声）和不具备证据的记录
  --> 话题聚类（embedding + 规则组合）
  --> 需求/痛点/疑问/风险标签分类
  --> 计算声量、独立作者数、互动量、情感分布、热度变化率和数据覆盖
  --> 生成 Insight 卡片（含 evidence_set_id、sample_size、data_coverage）
  --> 分析师打开证据，确认、修改标签或驳回
  --> 确认后的 Insight 可生成回应或内容 Action
```

失败流程一：重点平台（Facebook Groups）数据缺口。

```text
查询跨平台讨论
  --> Facebook Groups 连接器无有效数据（合规待确认或连接失败）
  --> 页面显示覆盖缺口横幅，说明受影响的分析范围
  --> 仍展示可用平台数据，但禁止显示「全平台总量」
  --> Insight 标记为「部分覆盖」，不输出跨平台对比结论
```

失败流程二：情感模型低置信度（讽刺/缩写/混合语言）。

```text
模型标注
  --> 讽刺语气、网络缩写、图片内文字或混合语言导致置信度低于阈值
  --> 该条内容进入人工复核队列
  --> 汇总指标使用「未判定」类别，不强行归为正面或负面
  --> 复核结果回写，用于改进分类模型的评估集
```

失败流程三：话题聚类版本不稳定（周间跳变）。

```text
每日聚类运行
  --> 新旧聚类 cluster_key 无法稳定匹配（主题融合或分裂）
  --> 保留 cluster_lineage 和版本记录
  --> 报告说明「本周话题与上周因聚类版本变化不可直接比较」
  --> 分析师可手动合并、拆分或重命名话题，操作记录入 annotation
```

```text
  --> 不纳入官方竞品表现比较，单独列入「待确认账号」
  --> 允许 Analyst 手动确认（标注确认依据）或移除
```

失败流程二：互动指标只有累计快照（无历史增量）。

```text

  --> 只能获得当前累计值（views、likes 累计，无 24h 增量）
  --> 不计算虚假的单日增速
  --> 展示「仅有累计快照，增量待下次采集对比」
  --> 以两次真实采集快照的差值计算后续增量，不回填历史
```

```text

  --> 没有公开字幕或平台未提供 transcript，audio 内容无法直接解析
  --> 只分析标题、描述、标签、评论和可用元数据
  --> 内容主题置信度标记「低：仅基于元数据」
  --> 不在报告中声称「已分析视频语义内容」
```

```text

+--------------------------------------------------------------------------------+

| 品牌相关度：高（与 Momcozy 可穿戴场景高度匹配）                               |

+--------------------------------------------------------------------------------+
| 左：趋势动量时序图（声量 / 创作者数 / 互动率趋势线）                         |
```

#### b) 交互流程

正常流程：

```text
系统采集 Hashtag 动态、热门 BGM、视频模板、时间快照（TikHub trending + Apify）
  --> 计算：声量、参与创作者数、互动率、跨平台出现次数、快照间增速
  --> 聚类为趋势实体（trend_key）并与母婴 ontology 进行语义匹配
  --> 抽取常见内容结构：开头形式、字幕风格、BGM 类型、时长区间、互动引导
  --> 评估品牌适配：相关度（话题与 Momcozy 品类）/ 可行性（内容制作门槛）
                   / 风险（平台合规、健康宣称）/ 时间窗（趋势生命周期估计）
  --> 生成 Trend Opportunity Card（含品牌切入角度和建议行动时间）
  --> 分析师选择跟进后转为 Trend Action，经审批后执行
```

失败流程一：趋势数据只有单个平台一次快照，无历史增量。

```text
趋势识别
  --> 没有历史快照或平台统计延迟未知（TikTok Creative Center 数据有 2-3 天延迟）
  --> 只标记为「候选趋势」，不输出增长率和峰值预测
  --> 不生成「正在快速上升」等确定性描述
  --> 等待后续快照或 Analyst 补充人工观察证据
```

失败流程二：热门 BGM 可见但商业使用权未知。

```text
BGM/Audio 分析
  --> 发现热门音频但商业使用权或地区适用性未在平台公开确认
  --> Action 生成时禁止直接写「使用该 BGM」
  --> 改为「参考该 BGM 的节奏和剪辑结构」
  --> 由内容团队确认版权授权后才能直接复用音频
```

失败流程三：跨行业趋势迁移评估为不适合母婴语境。

```text
可迁移创意评估
  --> 生活方式或娱乐趋势内容结构有趣，但与母婴产品语境不匹配
  --> 品牌相关度评分低于阈值
  --> 降级为「观察趋势」，不自动生成品牌参与 Action
  --> 记录分析师对降级原因的标注，用于优化评分模型
```

#### c) 状态清单

| 状态名称 | 触发条件 | 视觉标识 | 退出条件 |

| 候选趋势 | 单次或低覆盖信号，无历史快照 | 灰色 Candidate | 获得历史快照确认或被驳回 |

#### d) 依赖关系

```text
| 方向变化：从产品测评转向产后生活记录（30天 vs 90天主题分布对比）              |
```

#### b) 交互流程

正常流程：

```text
Admin 添加 Creator 公开账号（手动输入 handle，不从模型自动猜测）
  --> 系统验证账号存在性并标记平台
  --> 定期采集视频、标题、描述、字幕（如有）、评论和指标快照
  --> 聚合 30 天、90 天内容主题分布与内容形式
  --> 计算：高表现内容（超个人基线阈值）、方向变化信号（30天 vs 90天偏移）
  --> 识别商业披露信号（#ad/#sponsored/#gifted/paid partnership）
  --> 识别竞品提及和合作关系信号（注意：缺失不等于无合作）
  --> 生成合作时机评分卡（六维：内容匹配/受众场景/近期表现/商业空窗/品牌安全/数据完整度）
  --> Analyst 审核后生成 Creator Brief 或合作 Action
```

失败流程一：内容只能拿到标题和互动指标，无字幕或评论。

```text
Creator 内容采集
  --> 字幕不可用、评论被关闭或平台限制
  --> 画像明确标注「分析范围：仅标题、描述、元数据」
  --> 主题分析置信度降级
  --> 不把「未检测到竞品提及」解释为「没有竞品合作」
```

失败流程二：商业披露信号模糊（无 #ad，但有疑似赠品或品牌标签）。

```text
商业信号检测
  --> 未检测到明确 #ad / paid partnership，但出现品牌标签或「感谢 XX 提供产品」
  --> 标记「商业关系待人工确认」
  --> 合作建议必须包含披露确认步骤，不自动生成「可合作」结论
  --> 需要由内容负责人或法务流程确认后才能发起合作
```

失败流程三：方向变化信号来自发布频率异常而非真实转型。

```text
方向变化检测
  --> 近 30 天样本量低于最低阈值（如 <5 条视频）或发布频率骤降
  --> 不输出「Creator 已转向新赛道」
  --> 输出「主题分布出现变化，样本量不足以确认，建议继续观察」
  --> 扩展观察窗口至 60 天或等待下一采集周期
```

#### b) 交互流程

正常流程：

```text
S1-S4 四类分析模块产生经过人工审核的 Insight
  --> Action Engine 根据规则和模板生成候选 Action
  --> 评分：优先级（P1/P2/P3）/ 紧迫性（时间窗）/ 证据完整度 / 风险等级
  --> Analyst 编辑标题、角度、平台、负责人角色和验收指标
  --> 品牌负责人或内容负责人审批
  --> 状态变为「已批准 / 进行中」
  --> 执行者补充内容链接、发布时间和结果指标
  --> 复盘并标记：采纳有效 / 部分有效 / 无效 / 无法执行
```

失败流程一：证据不足（单条低置信度，无独立多源印证）。

```text
Action Engine 生成候选
  --> 结论只有单条低置信度证据或只有一个平台的孤立信号
  --> 生成「观察任务」而非「立即行动」
  --> 标记「证据待补充」，Action 不能进入「待审核」状态
  --> 等待后续采集周期补充证据后重新评估
```

失败流程二：建议涉及健康、安全或法律风险。

```text
Action Engine 生成候选
  --> 内容角度命中健康宣称、医疗功效、婴儿安全或 Creator 披露合规规则
  --> 自动添加「品牌 / 法务复核必填」标记
  --> 禁止生成对外承诺、疗效性表述或绝对化语言
  --> 通知品牌负责人，Action 不得在审批前变为「已批准」
```

失败流程三：趋势行动时间窗已过期。

```text
用户打开 Action
  --> trend_window_end 已超过当前时间
  --> Action 标记为「已过期」
  --> 不允许直接标记为「已执行」，保留为历史洞察
  --> 提示用户可从历史证据生成新的「常青内容 Action」
```

#### a) ASCII 图

```text
| 相关证据：[evidence_id_019] [evidence_id_031] [topic_cluster_2026-08-12-04]   |
```

#### b) 交互流程

```text
用户提出自然语言问题
  --> Agent 识别时间范围、平台、实体（产品/竞品/Creator）、分析类型和输出格式
  --> 若范围不明确，展示解析后的查询条件并请用户确认
  --> 调用：检索工具（证据 + 话题）/ 指标工具（声量 + 情感）/ 覆盖工具（数据状态）
  --> 先返回事实和证据（带 evidence_id），再返回解释与建议
  --> 用户可继续追问、调整时间范围、切换平台或生成 Action
```

失败流程一：问题超出当前数据覆盖范围。

```text
用户问「全平台用户怎么看 Momcozy M9」
  --> Agent 检查 coverage_report
  --> 确认当前只有 Reddit、YouTube 和自有账号数据
  --> 明确回答「当前可分析范围：Reddit + YouTube，Meta/TikTok 数据不可用」
  --> 不伪造全平台结论，不把缺失平台的空值理解为「没有讨论」
```

失败流程二：用户要求 Agent 直接对外执行。

```text
用户要求「马上去 Reddit 回复这条帖子」
  --> Agent 拒绝自动对外执行
  --> 生成内部回应草稿（带依据和风险提示）
  --> 用户必须通过外部平台按现有审批流程手动执行
  --> Action Board 同步创建「待审核：话题回应」
```

#### c) 状态清单

| 状态名称 | 触发条件 | 视觉标识 | 退出条件 |
|---|---|---|---|
| 解析中 | 正在识别查询意图和范围 | 蓝色 | 形成 Query Plan |
| 需要确认范围 | 时间、平台或实体含义不明确 | 黄色 | 用户确认或采用默认范围 |
| 检索中 | 正在调用工具获取数据 | 蓝色进度 | 工具返回结果或超时 |
| 有证据回答 | 找到足够来源，可输出有依据的结论 | 绿色 | 用户继续追问或结束 |
| 部分证据 | 数据覆盖不完整，结论范围受限 | 橙色 | 用户接受范围限制或调整查询 |
| 无证据 | 没有可验证结果（数据缺口或超出范围） | 灰色 | 扩大查询条件或明确提示数据缺口 |
| 需要人工复核 | 涉及风险信号、健康宣称或外部动作 | 红色 | 进入 Action 审批流程 |

#### d) 依赖关系

```text
用户查询（自然语言）
  --> Query Planner（意图识别 + 范围解析）
  --> 证据检索工具 / 指标查询工具 / 覆盖状态工具 / Action 工具
  --> 带来源和不确定性的结构化回答
  --> 可选：生成 Action 草稿 → Action Board
```

#### e) 待决问题

1. 是否需要保留跨会话对话记忆？推荐默认只保留工作区偏好和已确认词典，不保留个人用户信息。
2. 是否允许用户通过自然语言修改监测配置？推荐默认自然语言只生成配置草稿，保存前需要人工确认，防止误操作覆盖生产配置。


## 第四章：超越竞品的差异化功能

### 第 4.1 节 Evidence-first Social Action Chain

#### 1. 竞品为何未必具备这一能力

传统社媒监听平台以搜索、指标和报告为主；任务系统以执行为主。两者由不同数据模型和团队维护，导致「为什么做这个 Action」常需要人工复制链接、截图和填写说明。本产品把证据对象设计成 Insight 和 Action 的共同依赖，产品边界从「报告结束」延伸到「行动复盘」。

#### 2. 本产品如何实现

每条 Insight 必须包含 `evidence_set_id`。每个 Action 必须引用一个或多个 Insight。报告渲染器在没有 `evidence_set` 的情况下只能输出观察性提示，不能输出强行动语言。证据集包含：原始来源、采集时间、平台、数据能力等级、内容摘录（按合规策略）、指标快照、模型版本和人工审核记录。

#### 3. 交互流程

```text
原始内容（Reddit 帖子 / TikTok 视频 / YouTube 评论）
  --> 证据记录（evidence_id + source_url + collected_at + coverage_grade）
  --> 话题 / 竞品 / 趋势 / Creator Insight（绑定 evidence_set_id）
  --> Action 候选（继承 insight_id + evidence_set_id）
  --> 人工审核（可展开证据链验证）
  --> 执行结果回写（result_note + 实际效果数据）
  --> 复盘反馈（进入评估集优化 Action 推荐逻辑）
```

#### 4. 风险与应对

风险：来源内容被删除或链接失效，证据链断裂。
应对：保存允许保留的最小摘录、`provider_item_id`、采集时间和删除标记；不承诺永久复现原文；删除标记触发派生 Insight 的「证据已失效」提示，由 Analyst 重新核验。

---

### 第 4.2 节 Coverage-aware Intelligence（覆盖感知情报）

#### 1. 竞品为何未必具备这一能力

平台连接权限、字段、时效和数据供应商经常不同，普通看板更容易把缺失值隐藏在聚合结果中——用户看到一个数字，不知道它代表「全平台」还是「仅 Reddit」。本产品把覆盖状态作为一级业务数据，避免把某个平台没有数据误解为用户没有讨论，或把低样本结论展示为高置信度洞察。

#### 2. 本产品如何实现

每次报告和查询结果都带 `coverage_report`：平台、连接器、数据类型、时间范围、成功率、缺失字段、是否可比较、最后成功采集时间和限制原因。指标查询必须返回 `coverage_scope`。汇总函数禁止将 `null` 转换为 `0`，除非字段契约明确说明零值有业务含义。

#### 3. 交互流程

```text
用户查看跨平台用户洞察总览
  --> 系统先显示覆盖横幅（已覆盖平台 / 缺口平台 / 影响说明）
  --> 用户点击展开各平台贡献和缺口详情
  --> 指标卡显示「可比范围：Reddit + YouTube（2026-08-06 至 08-13）」
  --> 生成报告时自动写入「已覆盖范围」限制说明，不写「全平台」
```

#### 4. 风险与应对

风险：覆盖提示过多，用户产生「警告疲劳」，开始忽略。
应对：只在结论受缺口影响时显示高优先级覆盖提示；纯技术日志（如单次采集失败）进入数据质量页，不在分析主界面展示；覆盖状态按「影响业务判断」的程度分级展示。

---

### 第 4.3 节 Demand-to-Content Opportunity Graph（需求到内容机会图谱）

#### 1. 竞品为何未必具备这一能力

用户需求、内容资产、产品页面、客服 FAQ 和 Creator brief 通常分属不同系统。社媒工具不拥有内容生产闭环，内容工具也不保留社媒证据。本产品的差异不是「模型更聪明」，而是数据对象之间的关系被显式建模：用户在 Reddit 讨论的痛点可以直接跳转到现有 FAQ 缺口、待创作内容机会和匹配的 Creator 类型。

#### 2. 本产品如何实现

建立如下显式关系链：

```text
用户话题（topic_key）
  --> 需求 / 痛点 / 疑问（need_card / pain_point）
  --> 使用场景标签（pumping_at_work / night_pumping / travel）
  --> 可回答的问题（FAQ 机会）
  --> 内容角度（content_angle）
  --> 平台形式（TikTok POV / YouTube 教育 / Reddit 回应）
  --> Creator 类型匹配（IBCLC / 职场妈妈 vlog / 测评型）
  --> 现有产品页 / FAQ / 内容资产（关联检查）
  --> Action 结果（历史执行效果回查）
```

分析师可以从「法兰适配」话题卡，一键跳转到：当前 FAQ 是否已覆盖、哪种内容形式最适合、哪类 Creator 受众重叠度最高，而不是从零开始人工搜索。

#### 3. 交互流程

```text
分析师确认用户需求卡（如：法兰尺寸困惑）
  --> 系统展示「可回答问题」和「已有内容资产状态」
  --> 用户选择目标平台（TikTok / Reddit / YouTube）和目标受众
  --> Agent 生成 Content Brief 草稿（含角度、禁用表述、建议 Creator 类型）
  --> 分析师补充品牌要求、合规限制和资产需求
  --> 转为 Action，进入审批流程
```

#### 4. 风险与应对

风险：模型把弱相关需求错误关联到内容机会，生成质量差的 brief。
应对：关系类型区分「证据支持」「模型推测」「人工确认」；Content Brief 中的模型生成部分必须有置信度标注；内容负责人审批前必须看到「依据哪些证据」和「不确定性说明」。

---

### 第 4.4 节 Creator Timing and Brand Safety Card（Creator 时机与品牌安全卡）

#### 1. 竞品为何未必具备这一能力

Creator 发现工具通常优化静态筛选维度（粉丝数、互动率、赛道标签）。品牌安全和合作时机涉及：近期内容方向变化、商业披露历史、竞品合作状态、品牌禁区匹配，依赖时间序列分析和人工判断，不是单一排序分数能够覆盖的。

#### 2. 本产品如何实现

合作时机评分只作为排序辅助，不作为自动选人依据。评分拆成六项，并展示每项的证据和缺失项：

| 评分维度 | 说明 | 数据来源 |
|---|---|---|
| 内容匹配度 | Creator 近期主题与 Momcozy 品类的相关度 | 30天主题分布 |
| 受众场景契合 | Creator 受众评论显示的生活场景与目标用户重叠 | 评论关键词聚类 |
| 近期表现趋势 | 近 30 天互动表现相对个人基线是上升还是下降 | 指标快照 |
| 商业空窗信号 | 近期未检测到竞品披露信号（注：缺失不等于无合同） | 商业披露检测 |
| 品牌安全状态 | 近期内容无负面、争议或不当话题 | 内容分类 + 风险词 |
| 数据完整度 | 分析所依赖的字段覆盖率 | coverage_grade |

FTC 规则（来源 6）要求对有金钱、赠品或其他物质关系的推荐进行清晰披露，产品将 `disclosure_check` 作为 Creator 合作 Action 的必填确认字段。

#### 3. 交互流程

```text
Creator 近期内容时间线（30 天 / 90 天对比）
  --> 主题与形式分布变化检测
  --> 受众评论关键词与情感分析
  --> 商业披露检测（#ad / paid partnership / gifted）
  --> 竞品提及和品牌关系信号识别
  --> 六维时机与安全评分（含每维证据和缺失说明）
  --> Analyst 人工确认（不能自动生成「可合作」结论）
  --> 生成 Creator Brief（含披露要求、禁用表述、内容方向建议）
```

#### 4. 风险与应对

风险：公开信息不足（Creator 不用 #ad 标签，但实际有付费合同），系统误判为「无竞品合作」。
应对：显示「数据完整度」维度分数和说明；输出「公开信号未发现竞品合作，无法排除未披露关系」；Analyst 必须完成独立尽职调查后才能推进合作。


## 第五章：数据模型

### 5.1 数据模型原则

1. 原始事实、派生分析和人工判断分开保存，三者不混合在同一字段。
2. 所有跨平台 ID 作为字符串保存，不把平台雪花 ID 强制转换成整数。
3. 时间字段同时保存 `published_at`、`collected_at`、`metric_observed_at` 和 `valid_until`，避免把当前累计指标误当成历史时序数据。
4. 每个派生结论保存 `model_name`、`model_version`、`prompt_version`、`created_at` 和 `evidence_set_id`。
5. 列表型关系使用子表或关系表实现，不依赖超大 JSON 文档存储多值字段。
6. 覆盖缺口必须显式记录，不把缺失字段解释为零值或无数据，`null` 与 `0` 语义严格区分。
7. 删除定位设计：所有内容通过 `provider` + `provider_item_id` 可唯一定位，支持按合规要求清理原始内容和派生分析。

### 5.8 数据质量规则

| 规则 | 检查 | 失败处理 |
|---|---|---|
| 主键唯一 | `provider` + `provider_item_id` 不重复 | 报错并进入去重队列 |
| 发布时间存在 | `published_at` 不为空且可解析 | 标记 `invalid_timestamp`，不进入趋势计算 |
| 采集时间存在 | `collected_at` 不为空 | 采集任务标记失败，进入 DLQ |
| 指标语义 | 缺失指标为 `null`，不强制转为 `0` | 报告显示 `unavailable`，不输出对比结论 |
| 来源可追溯 | 原文链接、`provider_item_id` 或人工导入文件引用至少一个存在 | 禁止进入已验证 Insight |
| 词典可解释 | 话题、产品、竞品标签存在当前词典版本 | 进入「待标注」状态，不进入报告 |
| 数据新鲜度 | 当前报告范围内至少一个有效 `collected_at` | 显示数据过期横幅，报告标注覆盖范围 |
| 删除同步 | `provider_item_id` 被标记删除时，派生对象可定位 | 触发删除或重新生成摘要，记录审计日志 |
| 模型版本 | `annotation` 和 `insight` 带版本字段 | 版本缺失不允许发布报告 |
| 增量主键 | 汇总模型有 `unique_key` | dbt 或等价测试失败时阻止发布汇总层 |

### 5.9 数据保留与删除

| 数据 | 推荐默认 | 备注 |
|---|---|---|
| 原始 provider payload | 按合同和平台规则确定，初始 90 天 | 只为重放和审计服务，不展示给普通用户 |
| 标准化内容摘录与元数据 | 180 天滚动 | 保存最小必要信息和来源链接 |
| 汇总指标与话题趋势 | 24 个月 | 删除原文后需检查派生统计是否可保留 |
| Creator 内容画像 | 24 个月 | 账号下架或 Creator 要求删除时同步清理 |
| Action 与复盘记录 | 36 个月 | 作为内部决策记录 |
| 凭证与 token | 由 Secret Manager 管理 | 不写入数据库和报告正文 |

### 6.2 推荐部署路线

#### P0 试点（本地/云最小可行部署）

- 采集执行：Python connector worker，遵循现有 `tools/` 目录风格。
- 原始数据：本地或云对象存储按日期分区的 JSON/Parquet，`raw_object_ref` 指向文件路径。
- 分析存储：DuckDB，与现有 VOC 项目 `data/warehouse` 方向兼容。
- API 层：FastAPI，提供配置、报告、证据和 Action 接口。
- Agent 层：LangGraph，使用持久化 checkpointer；开发环境 SQLite，生产使用 PostgreSQL saver。
- 输出：Markdown 周报、JSON、CSV。

#### 生产增强（按需迁移）

- 控制面：PostgreSQL（配置版本、审计、权限）。
- 原始与明细：S3/GCS/Azure Blob + Parquet，按 `provider/year/month/day` 分区。
- 变换层：dbt 或等价 SQL/Python pipeline，使用增量模型、unique_key 和数据质量测试。
- 检索：OpenSearch，支持关键词检索、语义检索（向量）、过滤、聚合和证据钻取。
- 任务队列：SQS / Pub/Sub / Redis Streams 任选其一，必须有 DLQ、游标、节流和指数退避重试。
- 可观测性：结构化日志、采集成功率、字段缺失率、队列积压、LLM 成本、报告失败率。

### 6.3 Agent 工作流

```text
START
  --> parse_request（解析意图：时间/平台/实体/分析类型）
  --> build_query_plan（生成结构化查询计划，不自由发挥）
  --> load_coverage（检查平台覆盖状态，决定可用数据源）
  --> retrieve_evidence（调用检索工具，返回结构化证据列表）
  --> validate_sample_and_freshness（样本量/时效/覆盖门控）
  --> run_deterministic_metrics（规则指标：声量/情感/基线偏差，不用 LLM）
  --> run_domain_classifiers（话题/需求/竞品动作/趋势/Creator 分类）
  --> synthesize_fact_and_inference（事实与推断分离输出）
  --> evidence_gate（不满足门槛则降级结论，不输出高置信度表述）
  --> human_review_if_needed（风险/外部动作触发 interrupt）
  --> render_report_or_action（生成 Markdown 报告或 Action 草稿）
  --> persist_feedback（保存审核结果，更新评估集）
  --> END
```

关键约束：
1. `retrieve_evidence`、`run_deterministic_metrics` 和 `evidence_gate` 使用工具返回结构化数据，不交给 LLM 自由决定。
2. `synthesize_fact_and_inference` 必须输出结构化字段（`fact_text`/`inference_text`/`uncertainty_text`），不接受无法定位来源的自由文本。
3. Action 审批使用 LangGraph `interrupt`/`resume` 或等价状态机，所有外部动作必须经过人工确认。
4. 每次运行保存 `run_id`、`query_plan`、`tool_calls`、`model_version`、`prompt_version`、`evidence_ids` 和最终状态，支持回放和审计。

### 6.4 连接器接口

```python
class SocialConnector:
    provider: str      # 如 "reddit", "tiktok", "youtube"
    strategy: str      # 如 "tikhub_api", "apify_actor", "official_api"

    def validate_access(self, config: dict) -> dict:
        """返回权限、可采字段、地区限制和错误信息，不写业务数据。"""

    def build_query(self, scope: dict, window: dict) -> dict:
        """把统一监测范围（scope_id + 时间窗口）编译为平台查询参数。"""

    def collect(self, query: dict, cursor: str | None) -> dict:
        """返回原始载荷列表、下一游标、限流状态和覆盖信息；支持断点续传。"""

    def normalize(self, raw_item: dict) -> dict:
        """返回 CanonicalMention 标准格式，不执行模型推理，缺失字段返回 null。"""

    def collect_metrics(self, item_ids: list[str]) -> dict:
        """返回时间点指标快照；不支持的字段返回 null，不伪造历史增量。"""

    def delete_or_mark(self, provider_item_id: str) -> dict:
        """按平台规则删除本地数据或标记为不可用，返回审计记录。"""
```

连接器不可变约束：幂等（`provider` + `provider_item_id` 唯一键）、游标可恢复、原始载荷可审计、缺失字段不伪造、异常进入 DLQ、平台权限状态可见（`connector_registry` 实时更新）。

### 6.7 最大架构风险

最大风险不是 LLM 选型，而是外部平台数据权限与采集稳定性。工程可以写出连接器，但不能通过代码创造平台授权。缓解顺序：

1. 为每个平台建立 `capability_manifest`（可采字段、时效、费用、删除机制），在真实账号上运行连接测试。
2. 以 Reddit、YouTube、自有账号和人工导入建立可交付闭环（P0），不等待所有平台就绪。
3. Meta/TikTok 外部监听只在 Apify/TikHub 合同、官方批准明确可用时启用。
4. 把 provider 失败作为产品状态（`coverage_gap`）而非系统崩溃，报告中展示覆盖缺口。
5. 预留替换连接器能力，业务层不依赖某个爬虫的私有字段结构。

```text
    3.2 品牌适配评估
    3.3 建议参与时间窗
四、Creator 动态（S4）
    4.1 方向变化提示
    4.2 高表现内容
    4.3 合作机会

---
待人工确认事项
来源清单（evidence_set 引用）

```

报告写作规则：
1. 先写「事实」，再写「判断」，最后写「建议」，三者不混合。
2. 任何数字后面都写统计窗口、样本量、平台范围和指标快照时间。
3. 数据覆盖不完整时，标题使用「已覆盖范围内」，不写「全平台」。
4. 每条重大结论显示 `evidence_set_id` 或可点击的来源链接。
5. 不在报告中引用真实用户姓名、联系方式或非必要个人信息。

## 第十一章：开发者交接说明

### 11.1 实现顺序建议

1. **建立数据契约和离线 fixture 闭环**：先实现 `dim_monitor_scope`、`dwd_canonical_mention`、`dwd_evidence`、`ads_insight`、`ads_action` 的 schema，准备固定 JSON/CSV fixture（20 条 Reddit 帖子 + 10 条 YouTube 评论 + 5 条人工导入），用 SQL 检查幂等键、来源引用、时间字段和缺失值。
2. **实现 connector 接口层**：完成 `validate_access`、`build_query`、`collect`、`normalize`、`collect_metrics`、`delete_or_mark` 六个方法；游标断点续传；原始载荷写入 ODS；失败进入 DLQ。
3. **接入 Reddit 和 YouTube（P0 可验证）**：Reddit TikHub actor 已验证 67 条；YouTube Apify actor 待验证；两个平台通过幂等键测试和覆盖报告验证后，形成真实数据闭环。
4. **实现规则指标和基础分类**：话题聚类（embedding + 规则）、情感标注、需求/痛点标签、`evidence_gate` 门控逻辑。先确保事实可回溯，再接 LLM 摘要生成。
5. **实现 Markdown 周报和证据抽屉**：报告必须含覆盖说明、`evidence_set_id` 引用和不确定性标注；再实现 Action 候选生成、审批状态机（LangGraph interrupt/resume）和复盘字段。
6. **接入 TikTok 和 Instagram（P1）**：TikTok 通过 TikHub 竞品账号端点；Instagram 通过 Apify 自有账号；Facebook Groups 等待法务确认后启用；外部 Meta/TikTok 数据必须等待授权验证。
7. **引入 OpenSearch 语义检索和跨模块图谱（P2）**：先用 DuckDB FTS 完成基础检索，再迁移到 OpenSearch；需求到内容机会图谱在基础模块稳定后再建立。

### 11.2 最可能导致返工的三个决策

#### 决策一：外部平台数据采集路线（合规 vs 覆盖）

- 决策是什么：Meta（Facebook Groups / Instagram）和 TikTok 采用 Apify/TikHub licensed provider 路线，还是等待平台官方 Business API 批准？
- 安全默认：P0 只承诺 Reddit（TikHub 已验证）、YouTube（Apify 待验证）、自有账号和人工导入；所有外部连接器通过 `capability_manifest` 开关控制，未授权平台不自动启用。
- 需要改变方向的信号：法务确认某平台的 Apify actor ToS 合规性；或平台官方 API 审批完成，可确认字段、历史范围和删除同步能力。

#### 决策二：趋势数据来源（平台 Creative Center vs TikHub Trending API）

- 决策是什么：TikTok 趋势数据优先使用 TikHub `/web/explore/trending`（已有 Key），还是采购 TikTok Creative Center 导出？
- 安全默认：P0 用 TikHub trending 端点，标注「非官方 Creative Center 数据，延迟和覆盖范围以实际测试为准」，不对外承诺与官方趋势数据等价。
- 需要改变方向的信号：TikHub trending 端点数据质量验证后与业务预期差距过大；或 Creative Center API 开放商业访问。

#### 决策三：Creator 合作数据闭环（公开披露 vs 内部合同）

- 决策是什么：Creator 合作时机评分是否接入 Momcozy 内部 Creator 合作记录（CRM / 合同数据）？
- 安全默认：P0 只基于公开商业披露信号（`#ad`/`paid partnership`），明确说明「公开信号未发现竞品合作，不排除未披露关系」；不在报告中承诺「此 Creator 当前无竞品合同」。
- 需要改变方向的信号：Creator 合作团队提供 CRM 数据接口，且法务确认接入方式合规。

### 11.3 哪里要严格，哪里可以灵活

| 章节 | 标记 | 处理方式 |
|---|---|---|
| 数据契约（CanonicalMention、Insight、Action） | 约束 | `provider_item_id`、`evidence_set_id`、时间字段、模型版本不可省略；`null` 与 `0` 严格区分 |
| 平台能力矩阵 | 约束 | 不绕过权限；缺失字段用 `null` 和 `coverage_gap` 表达；不把抓不到写成「没有」 |
| 证据链设计 | 约束 | Insight 和 Action 必须有 `evidence_set_id`；报告无法引用证据时只能输出「观察提示」 |
| Agent 工作流 | 约束 | 工具取数，模型解释；风险和外部动作必须 human-in-the-loop；Action 审批不可跳过 |
| FTC 披露合规 | 约束 | Creator 合作 Action 必须包含 `disclosure_check` 字段；不能生成未注明商业关系的推荐 |
| 存储技术选型 | 建议 | 可以沿用 DuckDB，也可迁移 PostgreSQL、BigQuery、Snowflake；保留删除审计逻辑不变 |
| 搜索技术 | 建议 | OpenSearch 是推荐默认；已有搜索引擎可替换；P0 可用 DuckDB FTS 暂代 |
| 前端布局 | 发挥空间 | 可根据现有 Next.js 看板调整组件、颜色、图表和响应式布局 |
| 报告版式 | 发挥空间 | 可优化视觉层级；但不可隐藏覆盖说明、来源引用和不确定性标注 |
| LLM 供应商 | 建议 | 使用内部已批准模型；`model_name` 和 `model_version` 必须记录，不可省略 |

### 11.5 验收剧本

**剧本 1（离线 fixture 基础验证）**：在本地开发环境运行离线 fixture，加载 20 条 Reddit 帖子、10 条 YouTube 评论和 5 条人工导入记录，系统应生成唯一的 `CanonicalMention`、`Evidence` 和 `coverage_report`；用 SQL 检查 `provider` + `provider_item_id` 无重复；`null` 字段不被转为 `0`。

**剧本 2（Reddit 真实采集）**：在已配置有效授权的环境运行 Reddit 监测任务，选择一个已确认 Subreddit 和产品别名，任务应保存 `raw_object_ref`、`cursor`、采集日志和标准化内容；断开网络后重启，应从上次 cursor 恢复或记录明确失败原因。

**剧本 3（连接器失败状态）**：模拟连接器连续返回 401、429、schema 变化和零数据四种错误，系统应分别记录「授权失效」「限速暂停」「质量异常」「空结果」状态，并在报告中展示对应覆盖缺口，不把任何错误状态写成「无数据」或「0 条讨论」。

**剧本 4（Insight 证据链完整性）**：打开一条用户需求 Insight，依次查看事实（`fact_text`）、模型推断（`inference_text`）、不确定性（`uncertainty_text`）、样本量、覆盖范围和至少两条来源证据；点击「生成 Action」，Action 应自动继承 `insight_id` 和 `evidence_set_id`，默认处于「待审核」状态，不可直接变为「已批准」。

**剧本 5（Creator 合作合规检查）**：创建一条涉及 Creator 赠品或付费合作的 Action，系统应显示 `disclosure_check` 复核项和品牌安全复核项；在 `disclosure_check` 未标记为「已确认」时，Action 不能进入「已批准」状态；不能调用任何对外发帖或私信接口。

**剧本 6（趋势参与时间窗过期）**：找到一条趋势 Action，手动将 `trend_window_end` 改为过去时间，系统应将 Action 标记为「已过期」，不允许标记为「已执行」，保留为历史洞察，并提示可从历史证据生成常青内容 Action。

**剧本 7（报告可重现性）**：用同一份 fixture 和同一模型版本重复生成周报两次，事实数字、`evidence_id` 和 Action 来源应一致；更换模型版本后，系统应生成新的 `run_id` 和模型版本记录，不覆盖原有报告；分析师可并排比较两个版本的报告。
