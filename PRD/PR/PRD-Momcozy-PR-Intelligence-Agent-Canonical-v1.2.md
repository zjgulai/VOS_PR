## AI 速读卡

- 产品一句话：把核心媒体和编辑近期公开内容转成可追溯的选题、竞品评价、传播机会、媒体风险和待审批 PR Action。
- 核心循环：导入核心媒体池 → 检查来源与覆盖 → 采集或人工导入公开内容 → 解析媒体、edition 和署名 → 抽取主题、竞品观点和风险候选 → 生成 Media Brief → 人工审核 → PR Action → 结果回填。
- 目标范围：P0 聚焦美国英语吸奶器品类、11 家核心媒体和 48 位候选编辑；完整 P4 危机预警、广域媒体监测和多品类扩展进入 P1–P3。
- 硬约束：每条结论必须能回溯到来源和采集时间；区分事实、主张、推断与未知；AI 不自动联系记者、不自动发布声明。
- 推荐默认：优先使用获准媒体库、公开作者页、有效 RSS 和人工 URL 导入；媒体官方社媒只作内容发现，不直接代表编辑观点；不自动采集 LinkedIn。
- 发挥空间：看板视觉、报告版式、模型供应商、队列和云厂商可替换，但不能破坏媒体/edition/编辑归属、证据链、覆盖说明、关系约束和人工审批。
- P0 验收：11 家媒体和 48 位候选编辑可导入并回溯原工作簿；系统连续两轮生成媒体级 Brief，并为证据充分且身份已核验的编辑生成编辑级 Brief；事实可追溯、未知项可见、外部动作必须人工批准。
- 最容易翻车：把媒体账号当编辑账号、把未采到写成未报道、把赞助内容当独立编辑观点、把署名候选当已确认身份、把一般风险词命中当 Momcozy 风险。
- 超预期机会：编辑选题变化、竞品评价维度、同题冷却、关系冲突、资产缺口和行动结果共同形成可复用的媒体决策记录。

## 第一章：产品概述

### 1.1 产品定位

Momcozy PR Intelligence Agent 是一款面向跨境母婴品牌的核心媒体决策产品。P0 帮助 PR 团队持续追踪重点媒体和编辑的近期选题、竞品评价、Momcozy 传播机会与媒体风险，并在每条结论后展示来源、发布时间、署名状态、内容属性和不确定性，减少手工浏览作者页、复制链接和整理 pitch 背景的工作。

系统不是新闻搜索器，也不是自动写稿机。它必须完成五段闭环：

```text
核心媒体池与来源状态
    |
    v
采集与标准化
    |
    v
媒体、edition、编辑、主题、竞品观点与证据抽取
    |
    v
Media Brief / Opportunity / Media Risk / No-pitch 判断
    |
    v
PR Action → 人工审批 → 执行 → 复盘反馈
```

### 1.2 业务目标与问题定义

#### 1.2.1 业务目标

| 目标 | 结果定义 | 首期衡量方式 |
|---|---|---|
| 缩短媒体研究时间 | PR 从逐个浏览媒体和作者页转为审核已筛选证据 | 第 0 周与试点周的单份 Brief 人工工时对比 |
| 提高编辑判断准确性 | 选题和观点按媒体、edition、编辑和内容属性归属 | 署名归属 precision、重大事实修正率 |
| 提高传播机会可执行性 | 每个机会带媒体、编辑、角度、时机、资产缺口、关系约束和证据 | Opportunity 采纳率、Action 完整率、执行结果回填率 |
| 提前发现媒体风险 | 识别核心媒体中的负面、安全、质量、隐私和真实性风险候选 | 有依据风险率、人工确认结果、升级记录 |
| 统一媒体关系记录 | 联系历史、负责人、30 天冲突、冷却期和 no-pitch 原因可追溯 | 关系事件完整率、冲突拦截记录、月度更新完成率 |

| 如何评价竞品 | 哪些竞品和产品被测评，核心评价、证据维度和内容属性是什么 | Competitor View Cards |

| 接下来做什么 | pitch、seeding、补证据、观察或升级分别由谁负责 | PR Action Board |

### 1.3 Momcozy 业务上下文

项目内已有 deep research 对 Momcozy 的品牌、媒体位置、竞品和风险做了系统梳理，以下事实基线直接沿用，投产前需按最新时点重新核验。

#### 1.3.1 品牌与产品

Momcozy 是可穿戴吸奶器起家的跨境母婴 DTC 品牌，官网产品覆盖 Pregnancy、Bras and Postpartum、Pumping、Feeding、On The Go、Baby Care 等分类，产品包括可穿戴吸奶器（M5、M9、S9 Pro、S12 Pro、V1、V2、Air 1、W1 暖按摩吸奶器）、婴儿监视器、奶瓶清洗消毒器（KleanPal Pro）、婴儿背带、哺乳文胸等。标准型号存在 BP 别名映射，例如 M5 Smart 对应 BP380、M9 对应 BP223。来源：Momcozy 官网与 Support 页面，以及项目内 PR 调研方案。

产品含义：

1. 监测词典必须支持标准型号、BP 编码、用户俗称和拼写变体。
2. 品牌已从单一吸奶器扩展到多品类，PR 风险面从单品性能扩展到医疗器械合规、数字隐私、婴儿安全、专家伦理、心理健康和多国监管。
3. 品牌叙事存在「价值/舒适」与「性能领导者」的张力，PR 系统需要按 SKU 和评测维度分析，而不是按品牌名平均。

#### 1.3.2 媒体位置（来自项目内 PR 调研，投产前核验）

| 维度 | 已知事实 | 含义 |
|---|---|---|
| 权威背书 | Babylist 将 M5 Smart 列为 affordable，The Bump 将 V1 Pro 列为最佳整体免提、Air 1 为最隐形之一，Forbes Vetted 将 M5 列为 best value，Consumer Reports 将四款 Momcozy 吸奶器入测 | 价值、舒适、便携和特定形态有可赢维度 |
| 媒体缺口 | What to Expect、Good Housekeeping 美国版、Reviewed（USA TODAY）当前榜单未见 Momcozy，BabyCenter 评测页停留在 2024 年 | 存在明确的 pitch 和送测缺口 |
| 叙事张力 | Wirecutter 对 S9 Pro 使用「largest and least discreet」「clunky」等措辞，Modern Retail 将 Momcozy 置于「dupe/跟随者」框架 | 需要主动纠正或补齐证据，而非只压制负面 |

#### 1.3.3 风险基线（来自项目内 PR 调研，投产前核验）

| 风险 | 类型 | 已知事实 |
|---|---|---|
| KleanPal Pro 集体诉讼 | 产品安全 + 法律 | 2026-05 在 E.D.N.Y. 提起，指控高温消毒下塑料件脱落释放微塑料，ClassAction.org、TINA.org、Law360 已索引 |
| CPSC 公开 incident 报告 | 产品安全 | SaferProducts 上有 BS03 相关公开报告 |
| 美国参议院隐私问询 | 隐私 + 监管 | 2026-06 参议院 HELP 委员会致函关注 App 和联网产品数据处理 |
| 加拿大历史召回 | 监管 | Health Canada RA-72662，因缺少医疗器械许可召回，后于 2023-05 补发许可 |
| 评价真实性质疑 | 信任 + 合规 | Reddit 社区存在隐性营销/虚假评价指控，属未证实但需审计的信号 |

这些风险不能靠「正面内容压制」处理，必须由法务、隐私、产品安全、客服和 PR 共同形成事实包、响应门禁和审计记录。美国 FTC 自 2024-10 实施消费者评价与推荐规则，评价真实性和赞助披露同时是法律与声誉议题。P0 只负责在核心媒体范围内发现相关候选并交由人工升级；完整跨来源危机监测、分级和 War Room 属于 P1。

| 赛道 | 主要竞品 |

| 清洗/喂养电器 | Baby Brezza、Grownsy、Papablic |
| 婴儿监视器 | Nanit、Owlet、Infant Optics、VTech、Eufy |
| 背带 | Ergobaby、BabyBjörn、Tula |
| 产后/护理 | Frida、Haakaa |

系统应为每个竞品维护 Narrative Position Card：主张、证据、媒体接受度、反证和时间线。

### 1.8 研究范围与来源等级

P0 研究范围：

1. 导入并治理 `吸奶器核心媒体池` 中的 11 家媒体和 48 位候选编辑。
2. 跟踪美国英语吸奶器品类的近 30 天内容，并按可用性建立最多 180 天历史基线。
3. 分析媒体和已核验编辑的近期主题、内容形式、竞品产品、评价维度、核心观点和内容属性。
4. 识别 Momcozy 的传播机会、证据与资产缺口、关系冲突、同题冷却和 no-pitch 理由。
5. 识别核心媒体范围内与 Momcozy/竞品有关的负面、安全、质量、隐私和真实性风险候选，并由人工决定是否升级。
6. 生成 Media Brief、Opportunity Card、Media Risk Card、Coverage Report 和待审批 PR Action。

P1–P3 扩展范围：广域品牌与行业监测、完整 P4 危机预警、多品类与多市场、跨来源趋势、周报自动组装、战略决策和预算优化。

P0 来源优先级：

1. A 级：PR 团队确认的作者页、署名文章、内部媒体关系台账和人工提交 URL。
2. B 级：获准媒体库、媒体官方 RSS、站内公开元数据和允许保留的内容片段。
3. C 级：Google News、GDELT、Media Cloud 等开放发现线索，只用于发现并回链原站。
4. D 级：媒体官方 X、Instagram、Facebook、YouTube、TikTok 等公开账号，只用于内容发现和媒体级背景，不直接代表编辑观点。
5. E 级：记者数据库或 LinkedIn 等职业身份来源，只能在合同与自动化边界明确后启用；P0 默认人工核验，不自动抓取。
6. F 级：监管、客服、产品安全和其他内部一方数据，用于 P1 危机验证或经批准的 P0 反证，不是 P0 上线依赖。

#### b) 交互流程

正常流程：

```text
管理员导入核心媒体工作簿
  --> 选择 `吸奶器核心媒体池` 并预览列映射
  --> 系统在媒体分组内处理合并单元格，拆分媒体、edition、编辑和触点
  --> 系统生成稳定 ID、空值清单、冲突清单和 source_row_ref
  --> 管理员确认市场、语言、品类、来源类型和权利说明
  --> 系统预览可采字段、编辑身份状态和覆盖范围
  --> 测试连接
  --> 保存配置版本
  --> 调度器在下一周期使用新版本
```

失败流程一：凭证过期或额度不足。

```text
测试连接
  --> 返回认证失败或额度耗尽
  --> 状态变为待授权，隐藏原凭证
  --> 展示重新授权入口和影响范围
  --> 不删除历史数据，不继续重试无效请求
```

失败流程二：数据源可访问但全文或权利受限。

```text
测试连接
  --> 返回元数据但缺少全文或转发权利
  --> 创建 coverage_gap 记录
  --> 数据源标记为部分可用
  --> 报告显示字段缺口，不把缺失值当作 0
```

失败流程三：来源结构或作者页 schema 变化。

```text
定期采集
  --> RSS、媒体页或作者页返回结构变化
  --> 连接器进入质量保护，保存字段差异
  --> 相关媒体和编辑 Brief 暂缓更新
  --> 更新 adapter 并回放样本
```

#### a) 业务范围与界面


P0 名录以工作簿 `吸奶器核心媒体池` 为业务输入。系统必须导入全部 11 家媒体和 48 位候选编辑，但只有满足身份和证据门槛的记录才能生成编辑级判断。其他记录保留为媒体级 Brief、待核验编辑或覆盖缺口，不得补写编辑观点。

系统必须分开管理四类对象：

1. `Outlet`：媒体品牌。
2. `OutletEdition`：国家、语言和域名明确的媒体版本。
3. `Journalist` 与 `JournalistAffiliation`：公开职业身份和任职关系。
4. `Touchpoint`：作者页、媒体官方账号、编辑公开职业链接或人工输入入口。

记者画像只保存公开署名、公开职业信息、近期选题、报道形式、证据偏好、竞品观点、地域、受众和经过授权的关系历史。系统不保存敏感私人信息，不推断人格，不自动抓取 LinkedIn。

#### b) 工作簿导入流程

正常流程：

```text
管理员选择工作簿和 `吸奶器核心媒体池`
  --> 系统识别表头、合并单元格、超链接和原始行号
  --> 只在同一媒体分组内向下填充媒体级字段
  --> 拆分 outlet、edition、journalist、touchpoint、关系标签和 owner
  --> 生成稳定 ID 与 source_row_ref
  --> 输出导入预览、空值、重复、edition 冲突和无效链接
  --> 管理员确认或退回
  --> 保存名录版本
```

导入规则：

- `媒体`、`类型 / 区域`、`角色定位` 和媒体级 `Social Media` 可以在同一合并分组内继承。
- `Editor Name`、`Editor info/ Position`、`LinkedIn`、`个人简介`、`Cooperation type` 和 `Owner` 不得跨编辑继承。
- 一格内的多个社媒链接拆成多个 `Touchpoint`。默认实体归属为 `Outlet`。
- `LinkedIn` 只保存公开核验 URL 和核验状态；默认 `collection_policy=manual_verification_only`。
- 空值保存为 `null` 并进入导入报告，不使用其他编辑的数据补齐。
- 同名编辑、跨媒体任职或 edition 不明确时，生成候选关系，不自动合并。

失败流程一：工作簿格式或文件兼容异常。

```text
导入工作簿
  --> 解析器无法稳定读取或列结构变化
  --> 不写入正式名录
  --> 保存错误类型和受影响 sheet/列
  --> 提示管理员另存为标准 XLSX 或更新映射
  --> 重新预览并人工确认
```

#### c) 内容监测与 Brief 流程

```text
已确认媒体、edition、编辑和来源
  --> 读取近 30 天增量内容
  --> 按可获得且获准的数据补充最多 180 天历史基线
  --> 去重并识别首发、转载、榜单更新和内容属性
  --> 解析署名；无法确认时保留 author_text 并进入人工队列
  --> 抽取主题、内容形式、竞品产品、评价维度、核心观点和证据
  --> 识别 Momcozy 出现状态、机会、媒体风险和反证
  --> 检查 30 天联系冲突、同题冷却、关系状态和资产缺口
  --> 生成媒体级或编辑级 Media Brief 草稿
  --> PR Analyst 审核后创建 Opportunity、Media Risk 或 No-pitch Action
  --> 执行者回填联系、回复、发布和结果
```

P0 使用近 30 天内容回答「最近在关注什么」，使用最多 180 天历史内容判断是否发生选题变化。历史基线不完整时，系统必须展示实际覆盖起止日期和样本数。

#### d) 判断与失败路径

失败流程二：署名无法可靠归属。

```text
文章采集
  --> 署名缺失、同名、自由撰稿或任职关系不明
  --> identity_status = unverified
  --> 文章保留在 outlet/edition 层
  --> 不进入编辑级主题和观点汇总
  --> 分析师手动确认、拆分或拒绝
```

失败流程三：竞品观点来自赞助、affiliate 或转载内容。

```text
观点抽取
  --> 检测披露、商业链接、转载或内容属性不明
  --> sponsorship_status = sponsored / affiliate / syndicated / unknown
  --> 系统降低独立证据权重
  --> Brief 分开显示编辑观点、商业内容和无法判断
```

失败流程四：来源返回零内容或不可访问。

```text
定期采集
  --> 来源返回零内容、403/429、结构变化或作者页失效
  --> 区分 no_match、source_unavailable、rate_limited 和 schema_changed
  --> 不把结果写成「该媒体没有报道」
  --> Coverage Report 显示原因、最后成功时间和恢复动作
```

失败流程五：编辑刚完成同题报道或存在联系冲突。

```text
pitch 就绪判断
  --> 检查近 30 天同题内容和近 30 天关系事件
  --> 命中同题、重复 pitch、禁联、关系恶化或潜在利益冲突
  --> 生成结构化 no-pitch reason
  --> Action 保持 blocked 或观察
  --> 由负责人在有证据时解除
```

失败流程六：媒体内容命中一般风险词但与品牌/产品无关。

```text
Media Risk 候选
  --> 检查 Momcozy/竞品/产品实体、评价对象和证据片段
  --> 缺少实体相关性或只命中一般风险词
  --> 标记 unrelated 或 false_positive
  --> 不创建高优先级风险 Action
  --> 将人工结果写入排除规则评估集
```

```text
| 执行摘要 → 媒体与行业 → 竞品 → 核心媒体 → 机会与风险 → PR Actions → 来源附录      |
| 覆盖与限制：数据源 3/5 可用，受限社区未纳入，声量为去重后相关报道                 |
| 引用检查：重大结论 12/12 有 evidence_set_id，抽检通过                            |
| 操作：预览 | 编辑 | 发送审核 | 导出 Markdown/JSON/PDF | 版本历史                  |
+--------------------------------------------------------------------------------+
| 左：报告章节 | 中：引用与覆盖检查 | 右：审核与导出                              |
+--------------------------------------------------------------------------------+
```

#### b) 交互流程

正常流程：

```text
周期结束冻结数据
  --> 系统聚合已核验洞察、机会、风险和 Action
  --> 生成带引用和覆盖说明的草稿
  --> 检查引用覆盖、样本量、时间窗和模型版本
  --> Analyst 编辑并发送审核
  --> 品牌负责人批准后发布
  --> 回写接受/拒绝原因和行动状态
```

失败流程一：数据覆盖不完整。

```text
报告生成
  --> 检测到数据源缺口
  --> 标题使用已覆盖范围，不写全平台
  --> 显示缺口和影响范围
  --> 禁止把缺失当作零或无事发生
```

失败流程二：出现无来源结论。

```text
报告生成
  --> 检测到结论无 evidence_set_id
  --> 该结论降级为观察提示
  --> 报告不通过发布门槛
  --> 补充证据后重跑
```

失败流程三：模型版本变更导致结果不可比。

```text
报告生成
  --> 检测到模型或词典版本变化
  --> 报告标注版本和可比性说明
  --> 保留旧版本报告
  --> 不覆盖历史数字
```

#### c) 状态清单

| 状态名称 | 触发条件 | 视觉标识 | 退出条件 |
|---|---|---|---|
| 数据冻结 | 周期结束锁定数据 | 蓝色 Frozen | 报告生成 |
| 生成中 | 正在聚合和渲染 | 蓝色进度 | 草稿完成或失败 |
| 待审核 | 草稿等待 Analyst/品牌负责人 | 橙色 Review | 批准或驳回 |
| 已批准 | 审核通过可发布 | 绿色 Approved | 发布 |
| 已驳回 | 需要修改 | 灰色 Rejected | 修改后重新审核 |
| 已发布 | 报告对外或对内分发 | 深绿色 Published | 归档 |
| 生成失败 | 数据、模型或渲染错误 | 红色 Failed | 修复后重跑 |

#### d) 依赖关系

```text
verified insights + opportunities + risks + actions
  --> report aggregation
  --> citation and coverage check
  --> report draft
  --> human approval
  --> published report + feedback
```

#### e) 待决问题

1. 周报的接收人、分发渠道和审批链由谁定义。
2. 周报是否必须包含法务、产品安全和客服等跨部门附录。
3. 周报发布后是否自动生成下周的跟进任务。

## 第四章：超越竞品的差异化功能

### 第 4.1 节 Evidence-first PR Action Chain

#### 1. 竞品为何未必具备这一能力

这是基于公开产品形态的推断，不是对具体厂商内部实现的事实判断。传统媒体监测平台以搜索、指标和报告为主，任务系统以执行为主，两者由不同数据模型和团队维护，导致「为什么做这个动作」常需人工复制链接。本产品把证据对象设计成 Insight 和 Action 的共同依赖，产品边界从报告结束延伸到行动复盘。

#### 2. 本产品如何实现

每条 Insight 必须包含 evidence_set_id。每个 Action 必须引用一个或多个 Insight。报告渲染器在无 evidence_set 时只能输出观察性提示，不能输出强行动语言。证据集包含来源、采集时间、权威度、内容摘录、立场标签、模型版本和人工审核记录。推荐默认用关系表实现引用完整性，搜索引擎只负责检索，不作为唯一事实存储。

#### 3. 交互流程

```text
原始文档
  --> 证据记录
  --> 媒体/竞品/机会/风险 Insight
  --> Action 候选
  --> 人工审核
  --> 执行结果
  --> 复盘反馈
```

#### 4. 风险与应对

风险：来源内容被删除或链接失效。应对：保存允许保留的最小摘录、document_id、采集时间和删除标记；不承诺永久复现原文。

### 第 4.2 节 Claim-Evidence-Counterevidence Card

#### 1. 竞品为何未必具备这一能力

普通情感和话题标签容易把主张当事实，也容易忽略反证。PR 的核心判断往往依赖「主张、支持证据、反证、证据等级」四者，而不是单一情绪分数。这里的差异不是模型更聪明，而是把主张和证据作为一级对象显式建模。

#### 2. 本产品如何实现

建立 claim、evidence、counterevidence 三类对象，并维护 supports_or_refutes 关系。证据状态区分 verified_primary、verified_multiple_independent、credible_single_source、unverified_allegation、brand_claim、opinion、contradicted、resolved。每张卡显示事实窗口、市场、实体、支持证据、反证和未知项。

#### 3. 交互流程

```text
文档
  --> 主张抽取
  --> 支持证据与反证匹配
  --> 证据等级判定
  --> 人工审核
  --> 决策依据
```

#### 4. 风险与应对

风险：模型把相关性误判为因果或把转载当独立印证。应对：关系类型区分证据支持、模型推测、人工确认，报告不使用因果性语言，除非有业务验证。

### 第 4.3 节 核心媒体决策机制

#### 1. 竞品为何未必具备这一能力

媒体监测工具通常提供记者名单和提及，但未必把「编辑近期选题、竞品观点、证据偏好、冷却期、关系史」连成可执行的 pitch 决策。名单群发与按决策机制运营的差距来自数据对象之间的显式关系。

#### 2. 本产品如何实现

为每个核心媒体 edition 维护媒体级 Media Brief，并为身份已核验、证据充分的编辑维护编辑级 Media Brief。Brief 使用近 30 天信号回答近期关注，使用最多 180 天历史基线判断主题变化；同时记录报道形式、常用证据、竞品评价、内容属性、Momcozy 出现状态、媒体风险、覆盖缺口、最近接触和跟进日期。

pitch 就绪判断必须同时检查内容契合和关系约束。系统必须输出结构化 no-pitch 理由，包括证据不足、来源覆盖不足、编辑身份未核验、编辑刚完成同题、近 30 天已联系、品牌没有独立数据、潜在利益冲突、关系恶化或媒体风险未处理。无法判断时，状态必须是未知或待核验，不得默认为可 pitch。

#### 3. 交互流程

```text
工作簿名录 + 媒体/编辑公开内容 + 关系事件
  --> edition 与署名核验
  --> 近 30 天主题、形式和竞品观点
  --> 最多 180 天基线与选题变化
  --> Momcozy 机会、媒体风险和覆盖缺口
  --> 30 天联系冲突、同题冷却和关系约束
  --> pitch 就绪判断
  --> 人工确认后外联
```

#### 4. 风险与应对

风险一：公开信息不足造成误判。应对：显示来源状态、实际覆盖窗口、样本数和署名状态，允许输出无法判断，不把缺失解释为没有报道或没有关系。

风险二：媒体官方社媒被错误归到具体编辑。应对：`Touchpoint` 必须记录实体归属；只有经人工核验的编辑公开职业触点才能进入编辑级判断。

风险三：工作簿中的历史关系信息过期。应对：每条关系事件保存来源行、发生时间、负责人和最近核验时间；无法确认日期的历史文本只作备注，不触发自动冷却。

### 第 4.4 节 Trust Debt 信任债务指标（P2）

#### 1. 竞品为何未必具备这一能力

品牌对外的承诺若快于证据、合规、服务或问答准备，会累积信任风险。传统工具倾向于报告曝光和声量，缺少把未闭环高风险项、缺失证据的高频主张、逾期媒体承诺、未披露 seeding 和政策差异统一起来的内部优先级指标。

#### 2. 本产品如何实现

Trust Debt 不是对外发布的单一分数，而是内部优先级工具，用未闭环高风险项、缺失证据的高频主张、逾期媒体承诺、未披露 seeding、政策与实际数据流差异、重复客服问题等代理指标衡量。债务高的赛道先补事实和流程，不加大发声。

#### 3. 交互流程

```text
未闭环风险 + 缺失证据主张 + 逾期承诺 + 未披露关系
  --> Trust Debt 计算
  --> 按赛道排序
  --> 触发事实补齐或降级建议
  --> 纳入治理看板
```

#### 4. 风险与应对

风险：指标被当作对外声誉分数。应对：产品明确标注为内部优先级工具，不导出、不对外、不进入公开报告。

## 第五章：数据模型

### 5.1 数据模型原则

1. 原始事实、派生分析和人工判断分开保存。
2. 所有跨平台 ID 作为字符串保存。
3. 时间字段同时保存 published_at、fetched_at、metric_observed_at 和 valid_until。
4. 每个派生结论保存 model_name、model_version、prompt_version、created_at 和 evidence_set_id。
5. 列表型关系使用子表或关系表实现；下面 JSON 示例只展示单条记录，实际数据库不依赖一个超大 JSON 文档。
6. `Outlet`、`OutletEdition`、`Journalist`、`JournalistAffiliation` 和 `Touchpoint` 使用不同主键，禁止仅凭名称自动合并。
7. 所有工作簿导入对象保存 `source_file_ref`、`source_sheet`、`source_row_ref` 和 `import_version`。
8. 缺失、未采到、无匹配、来源失败和真实零值使用不同状态，不以空字符串或 0 混写。

### 5.4 核心媒体名录数据契约

| 对象 | 粒度 | 必填字段 | 关键约束 |
|---|---|---|---|
| `Outlet` | 一个媒体品牌 | `outlet_id, canonical_name, media_type, role_tags, status` | 不包含国家版和编辑字段 |
| `OutletEdition` | 一个国家/语言/域名版本 | `edition_id, outlet_id, country, language, canonical_domain, status` | P0 只能使用 `country=US, language=en` 的已确认 edition |
| `Journalist` | 一个公开职业身份 | `journalist_id, public_name, identity_status, verified_at` | 同名不自动合并；`verified_at` 可为空但状态必须是 `unverified` |
| `JournalistAffiliation` | 一段编辑与 edition 的任职关系 | `affiliation_id, journalist_id, edition_id, role, affiliation_status, source_url` | 文章只有在有效任职关系下才能归入编辑画像 |
| `Touchpoint` | 一个公开入口 | `touchpoint_id, entity_type, entity_id, platform, public_url, ownership_type, collection_policy, access_status` | 媒体官方账号不得归为编辑个人账号 |
| `ImportRecord` | 一条工作簿来源记录 | `import_record_id, source_file_ref, source_sheet, source_row_ref, import_version, raw_hash` | 所有导入对象均能回溯原 sheet 和行 |

核心名录对象的更新使用新版本，不覆盖历史值。编辑离职或转岗时，将 `JournalistAffiliation.affiliation_status` 更新为 `ended`，保留有效时间和核验来源。

### 5.12 数据质量规则

| 规则 | 检查 | 失败处理 |
|---|---|---|
| 文档去重 | text_hash 与 source_id 唯一 | 报错并进入转载聚类 |
| 工作簿可追溯 | 每个媒体、edition、编辑和触点有 source_sheet、source_row_ref、import_version | 禁止发布名录版本 |
| edition 明确 | P0 文档必须关联已确认的 US/en edition | 进入 edition_review，不参与 P0 Brief |
| 编辑身份 | journalist_id 非空时，identity_status 与 affiliation_status 均为 verified/active | 清空 journalist_id，降级到媒体级 |
| 触点归属 | 媒体账号与编辑账号的 entity_type、entity_id 和 ownership_type 一致 | 进入人工核验，不允许采集 |
| 发布时间存在 | published_at 不为空且可解析 | 记录 invalid_timestamp，不进入趋势计算 |
| 采集时间存在 | fetched_at 不为空 | 采集任务失败 |
| 转载归属 | is_syndicated 有 canonical_document_id | 声量统计按首发聚类 |
| 内容属性 | sponsorship_status 来自枚举且保留证据 | 未知时显示 unknown，不作为独立编辑背书 |
| 来源可追溯 | source_url、document_id 或授权导入引用至少一个存在 | 禁止进入已验证 Insight |
| 主张有证据 | 高影响 claim 至少一条 evidence | 降级为未验证主张 |
| 证据等级 | evidence_grade 来自枚举 | 缺失进入待标注 |
| 删除同步 | document 标记删除时派生对象可定位 | 触发删除或重新生成摘要 |
| 模型版本 | claim、insight、risk 带版本 | 版本缺失不允许发布报告 |
| 覆盖状态 | Brief 有实际覆盖起止日期、document_count 和 coverage_status | 禁止输出「未报道」等确定结论 |
| 媒体风险相关性 | media_risk 同时有关联实体、证据片段和人工 review_status | 不创建高优先级风险 Action |
| 关系约束 | 自动冷却事件有 occurred_at、reason_code 和有效期 | 无日期历史文本只作备注 |
| 增量主键 | 汇总模型有 unique key | dbt 或等价测试失败时阻止发布 |

### 6.3 推荐部署路线

#### P0 试点

- 名录导入：先支持标准 XLSX 的指定 sheet 和列映射，生成导入预览与冲突报告；原工作簿在进入验收前另存为标准 XLSX。
- 采集执行：Python connector worker，沿用现有 tools 目录风格；先接有效 RSS、作者页、人工 URL 和一个获准媒体入口。
- 原始数据：本地或云对象存储中的按日期分区 JSON/Parquet。
- 分析存储：DuckDB 与现有 data/warehouse 方向兼容。
- API：沿用 FastAPI，提供 Import、Registry、Brief、Coverage、Evidence 和 Action 接口。
- 工作流：先用显式状态机实现；需要多步骤恢复和人工中断时使用 LangGraph 或等价能力。
- 输出：Media Brief Markdown/JSON、Coverage CSV、Action brief；不生成完整 PR 周报。
- 明确不做：自动 LinkedIn 抓取、自动发信、完整 P4 War Room、368 家媒体扩面和全平台实时覆盖。

#### 生产增强

- 控制面：PostgreSQL。
- 原始与分析明细：S3/GCS/Azure Blob + Parquet。
- 变换：dbt 或项目现有等价 SQL/Python pipeline，使用增量模型、unique key 和数据测试。
- 检索：OpenSearch，支持关键词、语义检索、过滤、聚合和证据 drill-down。
- 任务：SQS/Pub/Sub/Redis Streams 任选其一，必须有 DLQ、游标、节流和重试。
- 可观测性：结构化日志、采集成功率、字段缺失率、队列积压、LLM 成本、报告失败率。

### 6.4 Agent 工作流

```text
START
  --> load_scope_and_registry
  --> validate_edition_identity_and_rights
  --> load_coverage_and_relationship_constraints
  --> collect_and_deduplicate
  --> resolve_byline_or_fallback_to_outlet
  --> classify_topic_competitor_and_content_type
  --> extract_claim_evidence_and_counterevidence
  --> detect_recent_focus_and_topic_shift
  --> detect_momcozy_presence_opportunity_and_media_risk
  --> evaluate_pitch_readiness_and_no_pitch
  --> evidence_gate
  --> render_media_brief_draft
  --> human_review
  --> create_action_if_approved
  --> persist_feedback
  --> END
```

关键实现要求：

1. 名录导入、采集、去重、edition、署名状态、实体分类、证据抽取和关系约束使用工具返回结构化数据，不让 LLM 自由决定结果。
2. 合成节点必须输出结构化字段，不接收无法定位来源的自由文本。
3. evidence_gate 在身份、样本量、覆盖、时间窗、内容属性、证据等级、模型置信度或关系规则不满足时降级到媒体级、未知或 no-pitch。
4. Media Brief、媒体风险、机会和 Action 审批使用可恢复的人工审核状态机。具体工作流技术可替换。
5. 每次运行保存 run_id、query_plan、tool_calls、model_version、prompt_version、evidence_ids 和最终状态，支持回放和审计。

### 6.5 分析框架

#### P0 Media Brief 判断门禁

P0 不用单一总分代替编辑和媒体判断。每份 Brief 先通过五道门禁：

1. 范围门禁：媒体 edition、市场、语言和品类均在已批准范围内。
2. 身份门禁：编辑级结论要求 `identity_status=verified` 且任职关系有效；否则降级到媒体级。
3. 证据门禁：事实、竞品观点、机会和媒体风险均有原 URL、发布日期、采集时间和证据片段。
4. 内容属性门禁：编辑内容、赞助、affiliate、转载和未知分开显示。
5. 覆盖门禁：实际时间窗、样本数和来源失败可见；覆盖不足时不得输出「未报道」或稳定偏好。

编辑选题变化至少比较近 30 天与可用历史基线。历史不足 180 天时可以比较实际窗口，但必须显示窗口和样本，不得假设完整 180 天。

Media Risk 候选必须同时满足：与 Momcozy、已确认竞品或吸奶器产品直接相关；存在明确负面、安全、质量、隐私或真实性主张；有可定位证据；通过人工复核。只命中一般风险关键词不能创建高优先级 Action。

#### P1 完整风险评分

以下风险总分供 P1 完整危机预警使用，不是 P0 上线门槛。风险总分是排序工具，不是事实结论：

```text
Risk = 0.25 x Severity + 0.20 x Velocity + 0.15 x Source Authority
     + 0.15 x Potential Reach + 0.10 x Corroboration
     + 0.10 x Brand Proximity + 0.05 x Persistence
```

各项 0-100，另设独立 Confidence。低置信高严重信号仍需快速核验，不能因证据不足沉底。

| 等级 | 分数或典型条件 | 系统动作 | 人工 SLA | 责任人 |
|---|---|---|---|---|
| Sev0 观察 | 低于 30、低权威单点 | 周度汇总 | 周报前 | Analyst |
| Sev1 关注 | 30-49、重复抱怨或核心媒体负评 | 工作队列 | 1 个工作日 | Regional PR |
| Sev2 升级 | 50-69、安全/隐私/真实性信号或明显增速 | 证据卡 + 主管通知 | 4 小时 | PR Lead + SME |
| Sev3 严重 | 70-84、权威媒体/监管/多源扩散 | War Room、暂停相关外发建议 | 60 分钟 | PR Director + Legal |
| Sev4 危急 | 85 及以上、生命安全/召回/执法/重大泄露 | 即时电话/多渠道升级 | 15 分钟确认、60 分钟首次事实简报 | Executive Crisis Team |

#### 机会评分

```text
Opportunity = 0.20 x Strategic Fit + 0.15 x Momentum + 0.15 x Media Receptivity
            + 0.20 x Evidence Readiness + 0.10 x Differentiation
            + 0.10 x Timing + 0.10 x Execution Feasibility - Risk Penalty
```

P0 可以先使用规则排序，不要求模型计算该分数。若启用分数，必须保存各组件、权重版本和人工调整记录；不得只保存最终总分。

#### 证据状态

| 状态 | 含义 |
|---|---|
| verified_primary | 原始一手来源验证 |
| verified_multiple_independent | 多个独立来源印证 |
| credible_single_source | 单一可信来源 |
| unverified_allegation | 未经证实的指控 |
| brand_claim | 品牌自述，非独立验证 |
| opinion | 观点而非事实 |
| contradicted | 存在反证 |
| resolved | 已解决 |

#### 效果衡量

按 AMEC 区分 outputs、out-takes、outcomes、impact，不把曝光和内容数量等同于理解、信任、偏好或业务结果。P0 业务结果使用 Brief 可用率、Opportunity/No-pitch 采纳率、人工研究时间、关系事件回填率和证据可追溯率衡量。风险提前量属于 P1 完整危机预警指标。

### 6.7 最大架构风险

最大风险不是 LLM 选型，而是 11 家核心媒体的内容入口、edition、编辑归属和使用权利。工程可以写出采集器，但不能通过代码创造版权授权、有效作者页或可靠任职关系。缓解顺序：

1. 为 11 家媒体分别建立 edition、作者页、RSS、人工 URL 和获准媒体库的 capability manifest，并运行真实连接测试。
2. 先保证媒体级 Brief 和人工 URL 降级，再逐步增加编辑级覆盖；不把 48 位编辑全部自动覆盖写成既有能力。
3. 署名或任职不确定时降级到媒体级，不自动猜测。
4. 把零内容、来源失败、限速和结构变化作为不同产品状态，Coverage Report 显示实际缺口。
5. 媒体官方社媒只作发现；LinkedIn 和其他职业身份来源默认人工核验。
6. 预留替换连接器，不让业务层依赖某个供应商的私有结构。

### 6.8 可替换技术原则

推荐默认使用现有 Python、FastAPI、DuckDB/Parquet 和 PostgreSQL 控制面；如果项目已有 BigQuery、Snowflake、ClickHouse、Airflow、Dagster 或其他队列，可以替换。LangGraph 可替换为等价的有状态工作流引擎。OpenSearch 可替换为已有搜索引擎。

不可替换的是：媒体/edition/编辑/触点对象边界、Document 与 Claim 字段语义、数据源 capability、署名状态、内容属性、关系事件、幂等键、cursor、raw reference、evidence_set、coverage_report、Action 审批状态机、删除定位和模型版本记录。完整风险分级与 SLA 在 P1 启用后同样不可破坏。

## 第十章：性能指标

指标分为三类：

- 硬门槛：证据、越权和数据语义要求，不得通过业务签字降低。
- 候选质量门槛：本版给出建议值，PR 与技术负责人签字后生效。
- Baseline 指标：先测第 0 周现状，再确定正式目标。

### 11.2 最可能导致返工的三个决策

#### 决策一：11 家媒体的来源与权利

- 决策是什么：每家媒体使用哪个作者页、RSS、公开页面、授权媒体库或人工 URL；允许保存全文、片段还是仅元数据。
- 安全默认选择：来源未确认时使用 `pending` 或 `manual_only`，只保留获准字段，不用爬虫绕过访问控制。
- 需要改变方向的信号：合同、法务或真实连接测试确认了字段、历史范围、刷新频率、保留期和删除方式。

#### 决策二：edition 与编辑身份

- 决策是什么：USA/UK 条目如何拆分；同名、自由撰稿、转岗和离职如何核验。
- 安全默认选择：P0 只聚合已确认 US/en edition；署名不确定时降级到媒体级。
- 需要改变方向的信号：PR 团队或获准记者数据库提供可审计的 edition 与任职关系。

#### 决策三：业务可用和 Action 责任

- 决策是什么：什么样的 Brief 算可用；什么样的机会、风险或 no-pitch 建议算被采纳；谁审核、执行和回填。
- 安全默认选择：使用第十章候选阈值和两轮人工评审；Action 没有 owner、证据或审批时不能进入执行中。
- 需要改变方向的信号：PR 团队提供 baseline、现行媒体关系流程和已签字的验收口径。

### 11.5 P0 验收剧本

验收剧本 1：导入标准化后的 `吸奶器核心媒体池`。系统应生成 11 个媒体对象、对应 edition 候选和 48 个编辑对象；媒体级合并单元格只能在所属分组内继承，编辑字段空值必须保留；每个对象能回溯 sheet 和原始行。

验收剧本 2：导入同时含 USA 和 UK/USA 的媒体记录。系统应生成 edition 复核任务；在美国版未确认前，该记录不能进入 P0 确定性 Brief，也不能与英国版内容混合。

验收剧本 3：加载一篇署名缺失、同名或任职不明的文章。系统应保留 `author_text`，将 `journalist_id` 设为 null，并把文章用于媒体级分析；系统不得把内容归到某位编辑。

验收剧本 4：加载编辑内容、赞助内容、affiliate 内容和转载内容各一条。Brief 应分别显示内容属性，赞助、affiliate 和转载内容不得被表述为独立编辑背书。

验收剧本 5：模拟来源正常返回零匹配、403、429、schema 变化和作者页失效。系统应分别显示 `no_match`、`source_unavailable`、`rate_limited`、`schema_changed` 和 `profile_invalid`；任何状态都不能被写成「该媒体没有报道」。

验收剧本 6：加载有明确竞品产品、评价维度和原文证据的文章。系统应生成 Competitor View，显示媒体或已核验编辑、内容属性、正/负/混合观点、核心依据、时间窗和 Evidence。

验收剧本 7：在已覆盖内容中没有观察到 Momcozy。系统应输出 `not_observed_in_covered_data`，同时显示实际覆盖窗口和来源；系统不得输出「该媒体未报道 Momcozy」这一无条件结论。

验收剧本 8：注入一条包含 `recall` 或 `lawsuit` 但与 Momcozy、竞品和吸奶器无关的文章。系统应标记 unrelated 或 false positive，不生成高优先级 Media Risk Action。

验收剧本 9：加载一条与 Momcozy 产品质量直接相关、证据明确的核心媒体负面评价。系统应生成待人工审核的 Media Risk Card；未经人工确认不得升级为已确认风险或自动发出外部回应。

验收剧本 10：导入编辑在近 30 天已有 pitch 事件，或编辑近期刚完成同题文章。系统应生成 `recent_contact_30d` 或 `same_topic_cooldown`，pitch readiness 必须为 blocked/cooldown，并显示 no-pitch 原因。

验收剧本 11：生成一份媒体级 Brief。Brief 必须包含范围、实际覆盖窗口、样本数、Recent Focus、Competitor View、Momcozy Presence、Opportunity、Media Risk、Relationship/Pitch Constraint、Uncertainty 和 Evidence。

验收剧本 12：为已核验且有足够文章证据的编辑生成编辑级 Brief；移除其任职证据后重新运行。新 Brief 应降级到媒体级，旧版本保留且标记身份依据已变化。

验收剧本 13：从 Brief 创建 pitch 或 seeding Action。Action 必须继承 `edition_id`、可空 `journalist_id`、`evidence_set_id`、关系约束和 no-pitch 状态；未批准时不能进入执行中，也不能调用任何发信或发布接口。

验收剧本 14：使用同一 fixture、规则和模型版本重复生成 Brief。事实、文档 ID、证据 ID、署名状态和关系约束应一致；模型或规则版本变化时生成新版本，不覆盖旧 Brief。

验收剧本 15：检查 P0 导航、输出和验收。系统可以识别媒体风险候选，但不能宣称已具备跨来源 `Sev0–Sev4`、危机 SLA 或 War Room；这些能力只在 P1 验收后启用。

### 11.8 研究与验证说明

本版使用项目内已有 deep research、Canonical v1.1、核心媒体工作簿和 2026-08-14 覆盖评估作为设计依据。本轮只读检查确认工作簿包含 11 家核心媒体和 48 位候选编辑；作者页、职位、负责人和关系字段存在不同程度缺失。现有 RSS 采集器只覆盖部分核心媒体，现场 dry-run 也暴露了来源返回零内容和一般风险词误报问题。因此，本版把 Source Capability、人工 URL 降级、署名门禁、媒体风险相关性和 Coverage 设为 P0 硬边界。

本版没有重新核验媒体榜单、编辑任职、外部监管事实或数据供应商合同。PR 团队提供的工作簿是业务输入，不等于全部内容已经过事实、权利和新鲜度确认。
