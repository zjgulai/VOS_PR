> 版本：v1.0 | 日期：2026-08-13

## 一、批次目标

批次 1 回答了「要解决什么问题」。批次 2 的核心目标是**验证剩余四个问题是否可落地**，并产出可执行的规格文档（而非代码）：

| 待定问题 | 批次 2 如何验证 | 对应任务 |
|---------|---------------|---------|
| 要抓取的数据 | 每个平台能否稳定取数 + 授权边界 + 存储契约 | T1 / T2 / T4 |
| 要分析的对象 | 竞品词典收敛为单一真源 | T3 |
| 要得出的结论 | 从问题拆到功能模块 + 结论与指标定义 | T5 |
| 产品形态（网站 + Agent） | P0 验收剧本可验证 | T6 |

---

## 二、任务清单（6 项）

### T1 数据源可行性实测矩阵 【P0，最关键】

- **目标**：验证 6 平台 × 第一梯队主源（Apify/TikHub）能否稳定取数，第二梯队是否可用作兜底。
- **现状**：Reddit ✅、TikTok ✅ 已出真实数据；Instagram / YouTube / Facebook Pages / Facebook Groups 均 `CODE_UNVERIFIED`。
- **产出**：`PRD/数据源实测记录.md`——每平台记录：验证命令、返回数据量、字段完整度、错误/限流、是否需降级到第二梯队。
- **验收标准**：每个平台 ≥5 条真实数据，且明确标注「缺失字段」（不把抓不到写成 0）。
- **依赖**：部署服务器网络（本机对外网 Connection reset）+ 用户已确认的 API Key。
- **需业务输入**：无（但需部署服务器访问方式）。

## 三、执行顺序（依赖关系）

```
Phase A（立即，纯分析/设计，不依赖外部）
  T3 竞品词典 ──┐
               ├─> T4 数据契约 ──> T5 功能模块 ──> T6 验收剧本
  （T5 可与 T3 并行）        （T4 依赖 T3 的词典字段）

Phase B（需业务/法务输入）
  T2 平台接入确认表（可先填技术部分，授权/费用留白待确认）

Phase C（需部署服务器网络）
  T1 数据源实测（依赖服务器访问 + API Key 就位）
```

**建议执行节奏**：T3 → T4 → T5 → T6 先串行跑通（纯文档，2-3 天），T2 同步发业务/法务确认，T1 在拿到服务器访问后立即实测。

## 四、边界（本批次不做）

- ❌ 不写新采集器代码、不建 DuckDB 生产表、不写周报/预警生成器
- ❌ 不做前端页面、不接飞书/Slack、不做 CI/CD
- ❌ 不推进 VOC 重构（仍推后）
- ❌ 不把「抓不到」写成 0，不把 LLM 推断当事实
